# 03 — Database Schema

PostgreSQL 16. Migrations via Alembic. The on-device SQLite schema mirrors this one minus the
sync/auth tables, plus a local `outbox` — see §8.

## Conventions

- **PK:** `id uuid` — UUIDv7, generated by the client (INV-16).
- **Ownership:** every user-owned table carries `user_id uuid NOT NULL REFERENCES users(id) ON DELETE
  CASCADE` and is indexed on it (INV-15) — **including every child of one**, such as `set_logs` and
  `planned_sets` ([ADR-013](decisions/ADR-013.md)). Every parent a child references has `UNIQUE (id,
  user_id)`, and the child's reference to it is composite, `(parent_id, user_id) → parent (id, user_id)`,
  so a row can never point at another user's row. A nullable link uses `ON DELETE SET NULL (parent_id)`.
  The listings below write the child's `user_id` and its reference once; the composite form is implied.
- **References to `exercises`** are `NO ACTION` (an exercise with history cannot be deleted, INV-11) and
  are checked by trigger: the exercise must be global or owned by the referencing row's user
  ([ADR-013](decisions/ADR-013.md)).
- **Sync columns:** every syncable table carries
  `created_at timestamptz NOT NULL`, `updated_at timestamptz NOT NULL`,
  `deleted_at timestamptz NULL` (soft delete, INV-11), `sync_version bigint NOT NULL DEFAULT 1`.
  Written below as **`‹sync›`** to avoid repeating them 20 times. **Which tables carry it is a
  classification, not a judgement call — see §11.** A missing `‹sync›` there is either deliberate
  or a bug, and §11 says which.
- **Units:** kg / m / s, in the column name (INV-01). Metric or imperial is presentation and never
  reaches storage ([ADR-008](decisions/ADR-008.md)).
- **Precision for loads** (INV-02): increments `numeric(10,6)`, loads `numeric(9,4)`. A narrower
  column silently pushes imperial prescriptions off the plate grid.
- **Percentages are integer basis points**, named `_bp` (250 = 2.5 %, 10000 = 100 %) — never a
  `numeric` fraction ([ADR-010](decisions/ADR-010.md)). Exact in Postgres, SQLite, Rust, Python and
  TypeScript alike, so a percentage can never round differently on the phone and on the server.
- **Language:** seeded reference rows carry a translation **key**, never a translated name. User text
  is stored exactly as typed (INV-27). A `*_key` column holds a full key (`'sport.swim_pool'`); a list of
  identifiers — `session_types`, `live_fields`, `detail_sections` — resolves as `<namespace>.<identifier>`
  (`session_type.easy`, `activity_field.distance`, `activity_section.splits`). Catalogs are nested JSON, so
  a dotted key is a path.
- **Enums:** Postgres native `ENUM` types. New values are added, never removed or renumbered.

## 1. Identity

```sql
users (

  email           citext UNIQUE NOT NULL,

  locale          locale_enum NOT NULL DEFAULT 'en',            -- en | pt-BR
      -- ADR-008, INV-27. Independent of unit_system. Stored server-side because the API writes
      -- emails and exports and cannot see the device. Defaulted from the device language.
  body_weight_kg  numeric(9,4) NULL,
  birth_date      date NULL,

      -- (set back to NULL). Not deleted_at, which is the sync soft-delete.

  -- user's password — but the wrap is a password-guessing oracle, so its KDF is never cheaper
  -- than password_hash's.

  privacy_key_salt    bytea NULL,   -- argon2id salt for the wrapping key, DISTINCT from the
                                    -- login password hash's salt
  privacy_key_kdf     text NULL,    -- wrapping KDF parameters, e.g. 'argon2id$m=65536,t=3,p=1';
                                    -- raised on the next password entry, never lowered

  id            uuid PK,
  user_id       uuid NOT NULL → users,
  token_hash    text NOT NULL,        -- never the token itself
  device_id     text NOT NULL,
  device_name   text NULL,
  issued_at     timestamptz NOT NULL,
  expires_at    timestamptz NOT NULL,

)

UNIQUE (token_hash)
-- Rotation sets revoked_at as well as replaced_by, so the retention purge (04 §7) sweeps replaced

  bucket_key   text NOT NULL,    -- '<rule>:<ip|account>:<HMAC-SHA256 of the subject>' — never an
                                 -- address or an email in the clear
  window_start timestamptz NOT NULL,
  hits         integer NOT NULL CHECK (hits > 0),
  PRIMARY KEY (bucket_key, window_start)
)
INDEX (window_start)             -- windows older than a day are purged

subscriptions (                -- 09-business-model.md, ADR-006
  user_id uuid PK → users,
  tier tier_enum NOT NULL DEFAULT 'trial',    -- trial | free | pro | coach
  trial_started_at   timestamptz NOT NULL,    -- = users.created_at
  trial_ends_at      timestamptz NOT NULL,    -- + 3 months, server-side; no card (FR-9.1)
  store store_enum NULL,                      -- apple | google
  store_product_id   text NULL,
  current_period_end timestamptz NULL,
  cancelled_at       timestamptz NULL,
  ‹sync›
)
-- Effective tier is a pure function of (tier, trial_ends_at, current_period_end, now) and lives
-- in the domain core. It gates FEATURES only — never a read of the user's own rows (INV-26).

body_weight_log (              -- weight over time; users.body_weight_kg is just the latest.
                               -- A bodyweight set's e1RM and tonnage read the entry ON OR BEFORE
                               -- the set's local_date, never the latest (INV-07, ADR-010).
  id uuid PK, user_id uuid NOT NULL → users,
  measured_on date NOT NULL, weight_kg numeric(9,4) NOT NULL, ‹sync›,
  UNIQUE (user_id, measured_on)
)

hr_zone_overrides (            -- optional; absent means derive from users.max_hr (INV-14)
  user_id uuid → users, zone smallint CHECK (zone BETWEEN 1 AND 5),
  min_bpm smallint NOT NULL, max_bpm smallint NOT NULL,
  ‹sync›,
  PRIMARY KEY (user_id, zone)
)
-- A sync root (§11) keyed naturally rather than by UUID. That is outside the letter of INV-16 and
-- inside its purpose: two devices independently derive the same key for zone 3, so the upsert
-- converges by construction — precisely what client-minted UUIDs buy everywhere else. Do not
-- "correct" this to a UUID PK; that would break the convergence it is preserving.

-- 04 §6. Zones MUST sync — a second device with no zones would upload untrimmed traces of the
-- same home, which is the failure the feature exists to prevent. They sync as ciphertext, because
-- a plaintext zone hands the server the exact coordinate the user asked to hide.
privacy_zones (
  id uuid PK, user_id uuid NOT NULL → users,
  ciphertext bytea NOT NULL,   -- {label, center_lat, center_lng, radius_m} as JSON, encrypted
                               -- with XChaCha20-Poly1305 under the user's privacy key
  nonce      bytea NOT NULL CHECK (octet_length(nonce) = 24),   -- fresh on every write
  ‹sync›
)
INDEX (user_id)
```

**No column here holds a coordinate, a radius, or a label** — including `radius_m`, because a
200 m circle and a 2 km circle say different things about what is being hidden. Trimming still
happens on the device (04 §6); the server's only role is to carry an opaque blob between the
user's own devices. See [04 §6](04-security-and-auth.md) for the key handling and for what a
password reset costs.

## 2. Exercise catalog

```sql
muscle_groups (
  id smallint PK, name_key text UNIQUE NOT NULL,   -- e.g. 'muscle.quadriceps' (INV-27)
  region muscle_region_enum NOT NULL   -- upper_push | upper_pull | legs | core | arms | other
)

exercises (
  id                uuid PK,
  owner_user_id     uuid NULL → users,     -- NULL = global seeded catalog (read-only, FR-2.2)
  forked_from_id    uuid NULL → exercises ON DELETE SET NULL,
  name_key          text NULL,
      -- global catalog only: a translation key, e.g. 'exercise.barbell_back_squat' (INV-27)
  name              text NULL,
      -- user exercises only: exactly as typed, never translated. A fork of a global exercise is
      -- user content — its translated name is copied here at fork time.
      -- CHECK: exactly one of name_key / name is set; name_key only where owner_user_id IS NULL.
  modality          modality_enum NOT NULL,   -- barbell|dumbbell|machine|cable|bodyweight|band|other
  primary_muscle_id smallint NOT NULL → muscle_groups,
  is_unilateral     boolean NOT NULL DEFAULT false,
  tracking          tracking_enum NOT NULL DEFAULT 'weight_reps',
                        -- weight_reps | reps_only | duration | distance_duration   (FR-2.3)
  load_increment_kg numeric(10,6) NULL,
      -- NULL → the modality default for the USER's unit system (INV-02). Global catalog rows always
      -- leave this NULL, so one seeded exercise is liftable for metric and imperial users alike.
      -- CHECK: load_increment_kg >= 0, and NULL wherever owner_user_id IS NULL.
  uses_bodyweight   boolean NOT NULL DEFAULT false,
      -- pull-ups, dips: volume AND e1RM use body weight + added load, the body weight being the
      -- body_weight_log entry on or before the set's date (INV-07, ADR-010)
  default_min_reps  smallint NULL,
  default_max_reps  smallint NULL CHECK (default_max_reps >= default_min_reps),
  notes             text NULL,
  ‹sync›
)
UNIQUE (owner_user_id, lower(name)) WHERE deleted_at IS NULL AND name IS NOT NULL
UNIQUE (name_key) WHERE name_key IS NOT NULL
INDEX (owner_user_id) INCLUDE (name)

exercise_secondary_muscles (      -- each secondary muscle is credited 0.2 of a set (FR-2.16)
  exercise_id uuid → exercises, muscle_group_id smallint → muscle_groups,
  PRIMARY KEY (exercise_id, muscle_group_id)
)
-- Trigger: muscle_group_id must differ from the parent exercise's primary_muscle_id. A muscle listed
-- as both would be credited 1.2 sets per set, silently inflating the one number FR-2.16 exists to
-- make trustworthy.
-- The 0.2 is NOT stored here. It is a single constant in the domain core, applied by the one
-- per-muscle attribution function (§9). A per-row weight column is the extension path if an exercise
-- ever needs a different share — never a special case in a query.
-- No user_id: a global exercise's muscles have no owner. The one child table without one; its policy
-- reads through exercises, whose own policy then applies (ADR-013). ON DELETE CASCADE from exercises.
```

```sql
modality_increments (            -- the INV-02 fallback, seeded for BOTH unit systems (ADR-008)
  modality     modality_enum,
  unit_system  unit_system_enum,
  increment_kg numeric(10,6) NOT NULL CHECK (increment_kg >= 0),
                                         -- imperial rows are exact kg equivalents of lb plates
  PRIMARY KEY (modality, unit_system)
)
```

| Modality | Metric | Imperial | Imperial, as stored |
|---|---|---|---|
| barbell | 2.5 kg | 5 lb | 2.267962 kg |
| dumbbell | 2.0 kg | 5 lb | 2.267962 kg |
| machine | 5.0 kg | 10 lb | 4.535924 kg |
| cable | 2.5 kg | 5 lb | 2.267962 kg |
| bodyweight (added load) | 1.25 kg | 2.5 lb | 1.133981 kg |
| band | 0 | 0 | 0 |
| other | 2.5 kg | 5 lb | 2.267962 kg |

Any exercise's increment can still be overridden (`exercises.load_increment_kg`). The usual reason
is someone who reads pounds but trains on kilogram plates, or the reverse.

## 4. Strength — performed workouts

```sql
workouts (
  id            uuid PK,                        -- client-minted (INV-16)
  user_id       uuid NOT NULL → users,
  routine_id    uuid NULL → routines,           -- ON DELETE SET NULL (INV-18)
  planned_session_id uuid NULL → planned_sessions,  -- ON DELETE SET NULL (INV-18)
  title         text NOT NULL,
  started_at    timestamptz NOT NULL,
  ended_at      timestamptz NULL,               -- NULL = in progress (INV-09)
  local_date    date NOT NULL,                  -- INV-17
  tz            text NOT NULL,
  notes         text NULL,
  perceived_fatigue smallint NULL CHECK (BETWEEN 1 AND 10),
      -- user annotation only. NOT RPE, NOT an engine input, never converted to RIR (INV-03).
  source        workout_source_enum NOT NULL,   -- manual | plan | routine
  ‹sync›
)
INDEX (user_id, started_at DESC)
INDEX (user_id, local_date)

workout_exercises (
  id uuid PK, user_id uuid NOT NULL → users,
  workout_id uuid NOT NULL → workouts ON DELETE CASCADE,
  exercise_id uuid NOT NULL → exercises,        -- NO ACTION: never orphan history (INV-11, ADR-013)
  order_index int NOT NULL, superset_group smallint NULL, notes text NULL,
  planned_exercise_id uuid NULL → planned_exercises,   -- ON DELETE SET NULL (INV-18)
  rest_seconds    smallint NULL,        -- NULL = no rest timer; never an invented default
  target_min_reps smallint NULL,
  target_max_reps smallint NULL,
  target_rir      smallint NULL CHECK (target_rir IS NULL OR target_rir BETWEEN 0 AND 10),
      -- the four above are COPIED from the routine (or plan) when the workout starts, and editable during it:
      -- editing the routine afterwards must never move a timer that is already running (task 004 stage 5).
      -- target_rir is shown beside a set as a target and is never written into set_logs.rir (INV-03).
  ‹sync›
)
INDEX (workout_id, order_index)
INDEX (exercise_id, workout_id)                 -- "last time" lookups, §9

set_logs (
  id uuid PK, user_id uuid NOT NULL → users,
  workout_exercise_id uuid NOT NULL → workout_exercises ON DELETE CASCADE,
  set_index    smallint NOT NULL,               -- 1-based, contiguous per exercise
  set_type     set_type_enum NOT NULL DEFAULT 'working',
                   -- warmup | working | drop | backoff | amrap    (INV-04)
  weight_kg    numeric(9,4) NULL CHECK (weight_kg IS NULL OR weight_kg >= 0),   -- INV-02 precision
  reps         smallint NULL CHECK (reps IS NULL OR reps BETWEEN 0 AND 1000),
  rir          smallint NULL CHECK (rir IS NULL OR rir BETWEEN 0 AND 10),   -- INV-03
  distance_m   numeric(9,3) NULL,               -- tracking = distance_duration. Not int: 100 ft typed is 30.48 m,
                                                -- and an integer read it back as 98 ft (task 004 stage 5c, INV-01)
  duration_s   int NULL,                        -- tracking = duration
  is_completed boolean NOT NULL DEFAULT false,
  completed_at timestamptz NULL,
  planned_set_id uuid NULL → planned_sets,      -- FR-3.15, the plan↔log link; ON DELETE SET NULL (INV-18)
  ‹sync›
)
UNIQUE (workout_exercise_id, set_index) DEFERRABLE
INDEX (planned_set_id) WHERE planned_set_id IS NOT NULL
```

**Note:** `weight_kg`/`reps`/`rir` are all nullable because a set exists (pre-filled from the
plan) before it is performed. `is_completed = true` requires the fields its `tracking` mode needs
— enforced in the service layer, not the DB, because the requirement depends on the exercise.

**`completed_at` is when the set was done, and `updated_at` is when the row was written.** They usually
coincide, and they diverge on a workout logged retroactively (FR-2.13): its sets carry the workout's
chosen end as `completed_at`, the honest upper bound on when they were done, while `updated_at` stays
the real time of the write, because last-write-wins sync compares `updated_at` (NFR-4) and a backdated
one would lose to any stale copy ([task 004](tasks/004-exercise-catalog-and-logging.md) stage 6).

```sql
personal_records (                 -- derived, rebuildable from set_logs; cached for speed
  id uuid PK, user_id uuid NOT NULL → users, exercise_id uuid NOT NULL → exercises,
  kind pr_kind_enum NOT NULL,      -- max_weight | best_e1rm | max_reps_at_weight | best_session_volume
  value        numeric(12,4) NOT NULL,
  weight_kg    numeric(9,4) NULL, reps smallint NULL,
  rir          smallint NULL CHECK (rir IS NULL OR rir BETWEEN 0 AND 10),   -- INV-03
  set_log_id   uuid NULL → set_logs ON DELETE CASCADE,     -- a cache row dies with its source
  workout_id   uuid NULL → workouts ON DELETE CASCADE,
  achieved_at  timestamptz NOT NULL,
  computed_at  timestamptz NOT NULL     -- when this cache row was last rebuilt
)
CHECK (kind <> 'max_reps_at_weight' OR (weight_kg IS NOT NULL AND reps IS NOT NULL))
UNIQUE (user_id, exercise_id, kind) WHERE kind <> 'max_reps_at_weight'
UNIQUE (user_id, exercise_id, weight_kg) WHERE kind = 'max_reps_at_weight'
    -- current best only; history lives in set_logs. max_reps_at_weight is one record per
    -- load, every other kind one row per exercise (task 004 stage 7: the single key
    -- (user_id, exercise_id, kind) could hold the reps record of one load only)
```
**Which row a record points at.** The rebuild folds each exercise's finished sessions oldest first through the
core's `standing_records()`, so `set_log_id`, `workout_id` and `achieved_at` name the **earliest** set that reached
the standing value — a later tie is not a record (INV-10). `achieved_at` is that set's `completed_at`; a session
volume belongs to no one set, so it takes the workout's `ended_at` and a NULL `set_log_id`. For `max_weight` and
`max_reps_at_weight` the `weight_kg` is the total load, body weight included (below). For the other two kinds it is
the load of the set that set it, or NULL for a session volume.

Deload sets are excluded when computing these (INV-08). For bodyweight exercises, `max_weight` and
`best_e1rm` compare **total** load — body weight on the set's date plus added load — displayed as
"BW + 20 kg" (ADR-010).

**No `‹sync›`, deliberately.** This is a derived cache, rebuildable from `set_logs`, and the device
does not have the table at all (§8) — it recomputes locally. A row that never crosses the wire has
no use for sync columns, and carrying them would imply a conflict-resolution question that does
not exist. Classified as *derived* in §11.

## 5. Strength — the planner

```sql
progression_rules (
  id uuid PK, user_id uuid NOT NULL → users,
  name text NULL,                     -- named, reusable presets
  strategy  progression_strategy_enum NOT NULL,
      -- v1:  linear_load | double_progression | percent_1rm | rir_autoregulated | fixed
      -- v2:  cycle_pattern                                                  (FR-3.2)
      -- Chosen by the user, switchable mid-block (FR-3.6a). No product default.
      -- The v2 value is in the enum from day one: adding a strategy later is an engine
      -- branch, never a migration.

  load_step_kg   numeric(10,6) NULL,     -- linear_load / double_progression; INV-02 precision
  load_step_bp   integer NULL CHECK (load_step_bp > 0),   -- alternative to load_step_kg; 250 = 2.5 %
  rep_step       smallint NULL DEFAULT 1,
  min_reps       smallint NOT NULL,      -- INV-05, the user's "min/max rep limits"
  max_reps       smallint NOT NULL CHECK (max_reps >= min_reps),
  min_rir        smallint NOT NULL DEFAULT 0 CHECK (BETWEEN 0 AND 10),
  max_rir        smallint NOT NULL DEFAULT 4 CHECK (max_rir >= min_rir),
  rir_mode       rir_mode_enum NOT NULL DEFAULT 'per_exercise',   -- per_exercise | per_set
      -- FR-3.8a. AUTHORING granularity only: whether one target RIR is set for the whole
      -- exercise or a different one per set. Storage is per-set either way — planned_sets.
      -- target_rir always exists. Inherits the FR-3.6 cascade (exercise → mesocycle → user).
  rir_offsets    jsonb NULL,
      -- per_set only: an integer offset per working-set position, e.g. [2, 1, 0]. A set's target
      -- RIR = the exercise target + its offset, CLAMPED into [min_rir, max_rir] (INV-05, ADR-010).
      -- A set beyond the array's length takes offset 0. Ignored under per_exercise.

  rir_start      smallint NULL CHECK (BETWEEN 0 AND 10),   -- rir_autoregulated: RIR at cycle 1
  rir_end        smallint NULL CHECK (BETWEEN 0 AND 10),   -- …and at the last working microcycle
  percent_wave_bp jsonb NULL,            -- percent_1rm: integer basis points [7000, 7500, 8000, …]
  baseline_e1rm_kg numeric(9,4) NULL,    -- percent_1rm: REQUIRED (CHECK). The starting reference, so
                                         -- generation is total even with no e1RM in history.
                                         -- Held unchanged when a cycle yields none (FR-3.2c,
                                         -- INV-07) — the engine never estimates one.
  cycle_pattern  jsonb NULL,             -- cycle_pattern (v2): a repeating step list, tiled

  failure_policy failure_policy_enum NOT NULL DEFAULT 'hold',  -- hold|repeat_cycle|reduce_load
  failure_load_bp integer NULL DEFAULT 9000 CHECK (failure_load_bp BETWEEN 1 AND 10000),  -- reduce_load
  rounding       rounding_enum NOT NULL DEFAULT 'nearest',     -- nearest | down | up (ADR-010)
  ‹sync›
)

mesocycles (
  id uuid PK, user_id uuid NOT NULL → users,
  name text NOT NULL,
  goal meso_goal_enum NOT NULL,          -- hypertrophy | strength | peaking | maintenance
  start_date date NOT NULL,
  num_microcycles smallint NOT NULL CHECK (BETWEEN 2 AND 52),      -- FR-3.1
  default_microcycle_days smallint NOT NULL DEFAULT 7
      CHECK (BETWEEN 1 AND 28),          -- 7 is a DEFAULT, never an assumption (INV-25)
  deload_mode deload_mode_enum NOT NULL DEFAULT 'none',
      -- none | every_n_microcycles | manual  (FR-3.1b) — 'none' is a real choice
  deload_every_n_microcycles smallint NULL CHECK (>= 1),
      -- CHECK: set iff deload_mode = 'every_n_microcycles'
  deload_final_cycle boolean NOT NULL DEFAULT false,
  deload_set_bp   integer NOT NULL DEFAULT 5000,   -- 50 % of sets (ADR-010)
  deload_load_bp  integer NOT NULL DEFAULT 6000,   -- 60 % of load, re-anchored by round_to_increment
  deload_rir_bump smallint  NOT NULL DEFAULT 2,
  default_rule_id uuid NULL → progression_rules,          -- FR-3.6 middle tier
  status meso_status_enum NOT NULL DEFAULT 'draft',        -- draft|active|completed|abandoned
  ‹sync›
)

microcycles (
  id uuid PK, user_id uuid NOT NULL → users,
  mesocycle_id uuid NOT NULL → mesocycles ON DELETE CASCADE,
  cycle_number smallint NOT NULL,
```

### The INV-06 backstop

Two triggers, identical in Postgres and SQLite ([ADR-013](decisions/ADR-013.md)). Each reads a marker the
row already carries, so neither needs a session variable:

- **`planned_sets`** (and `planned_cardio_sessions`): an `UPDATE` that changes a prescription —
  `set_index`, `set_type`, any `target_*`, `was_clamped`, `deleted_at` — while the owning cycle's status is
  not `projected` is rejected **unless `NEW.origin = 'user_edited'`**.
- **`microcycles`** (and `cardio_plan_microcycles`): an `UPDATE` with `NEW.last_write_kind = 'engine'` is
  rejected if the cycle was not `projected` and any of its columns change, **or** if it lowers
  `engine_version`.

A row rewritten unchanged passes, so sync can resend whole rows. Inserts are not guarded — a new device
pulls completed cycles as inserts — and plan rows are hard-deleted only by account deletion (INV-11).

### Why the plan is materialised
Four levels of rows for a 12-cycle block is a lot of rows (~1 500 planned sets for a 5-session
cycle) and the obvious alternative is to compute prescriptions on read. We materialise because the
user must be able to *see* cycle 9 today, *edit* cycle 9 today, and have that edit survive. See
[ADR-002](decisions/ADR-002.md) for the full argument and the rejected alternatives.

### Dates are derived, and re-derived on change
`microcycles.starts_on` is computed by walking the block: cycle 1 starts on
`mesocycles.start_date`, and each subsequent cycle starts `length_days` after the previous one.
A planned session's real date is `microcycle.starts_on + (day_index − 1)`.

**Changing one microcycle's `length_days` shifts the start date of every cycle after it**, which
must re-derive in one transaction — and, per INV-06, may only touch cycles that have not started.
This is the price of decoupling training from the calendar, and it is why the dates are stored
rather than computed on every read: a session's date must be stable enough to attach a workout and
a reminder to.

## 8. On-device SQLite

Same tables, with these differences:

1. **Omitted:** the four server-only auth tables — `refresh_tokens` (tokens live in the OS keychain,
   04 §3), `password_reset_tokens`, `email_verification_tokens` and `account_deletion_tokens` (task 019) — the server's
   `rate_limit_buckets` ([ADR-015](decisions/ADR-015.md)), and **both derived
   caches** — `personal_records` (recomputed from local `set_logs`) and `user_track_progress`
   (folded from local `xp_awards`). Both ledgers sync, so the device can always rebuild the
   numbers itself; shipping the folded answer as well would only give it something to disagree
   with. `users.password_hash` is omitted too: it never leaves the server.
2. **Added:** `raw_gps_points` (§6, never synced) and:
   ```sql
   outbox (
     id integer PK AUTOINCREMENT,
     entity text NOT NULL, entity_id text NOT NULL,
     op text NOT NULL,                    -- upsert | delete
     payload text NOT NULL,               -- JSON snapshot
     created_at integer NOT NULL,
     attempts integer NOT NULL DEFAULT 0,
     last_error text NULL, next_attempt_at integer NULL
   )
   sync_state ( key text PK, value text )   -- pull cursor, last sync time
   ```
3. **Types:** `uuid`→`text`, `timestamptz`→`integer` epoch ms, `numeric`→`real`,
   `boolean`→`integer`, `jsonb`→`text`.
4. **No enums** — `text` plus a CHECK constraint.
5. **`privacy_zones` is stored decrypted on-device** (`label`, `center_lat`, `center_lng`,
   `radius_m` as ordinary columns). The device already holds raw GPS points, so encrypting the
   zone next to them would protect nothing; the trimmer needs the plain values. Encryption happens
   on the way out, in `src/sync/`, and decryption on the way in.
6. **Server-only integrity.** Row-level security, the composite ownership keys and the exercise-owner
   trigger exist only in Postgres: a device holds one user's rows. The `user_id` columns themselves are
   on the device too, so both schemas keep the same column names ([ADR-013](decisions/ADR-013.md)). The
   INV-06, `day_index` and secondary-muscle triggers exist in both.
7. **Dates** are ISO `text` (`'2026-09-12'`), and `xp_awards`' key has no `NULLS NOT DISTINCT`: a second,
   partial unique index over `(user_id, source_kind, reason) WHERE source_id IS NULL` does its job.

The Alembic↔Drizzle comparison ([task 002](tasks/002-database.md)) fails on any table or column name that
differs between the two, except where this list says so.

Two migration streams (Alembic server-side, Drizzle client-side) must be kept compatible; the
rule is in [06-operations.md](06-operations.md) §4.

## 9. Indexing notes

Beyond the indexes listed inline:

- `set_logs` is the hot table. The dominant query is "last performance of exercise X for user U"
  (FR-2.12), which crosses three tables. Add
  `INDEX workout_exercises (exercise_id, workout_id)` and rely on `workouts (user_id, started_at
  DESC)`. If it is not fast enough, denormalise `user_id` and `performed_at` onto `set_logs`
  rather than adding a cache — measure first.
- Analytics (FR-2.16, volume per muscle per microcycle) is a 4-table join over a date range.
  Acceptable because analytics run on-device over one user's own history ([06 §9](06-operations.md));
  the moment it is not, it becomes a materialised view refreshed on workout completion, not an
  ad-hoc denormalisation.
- **The query returns rows, not totals.** It selects each counted set with each muscle it touches and
  that muscle's role, primary or secondary. The **domain core** applies the 1.0 / 0.2 weighting
  (FR-2.16). A `SUM(CASE WHEN secondary THEN 0.2 …)` in SQL would be a second copy of the rule — the
  exact divergence INV-04 forbids for `is_counted_set()`.
- `activity_streams.data` is large; keep it out of `SELECT *` by never using `SELECT *`.
  Postgres TOASTs it automatically.

| exercise | **NO ACTION** — archive instead; history must survive (INV-11). Not `RESTRICT`, which would fail an account deletion depending on cascade order ([ADR-013](decisions/ADR-013.md)) |
| routine | `workouts.routine_id` → NULL |
| mesocycle / cardio_plan | plan rows CASCADE; `workouts.planned_session_id` → NULL (INV-18) |
| workout | its exercises and sets CASCADE (they have no meaning alone) |
| cardio_activity | streams and segments CASCADE |
| sport_profile | **RESTRICT** — seeded reference data; a sport with activities is never removed |

## 11. Sync classification

`‹sync›` is a **classification, not a checklist item.** Two tables were originally missing it for
opposite reasons — one an oversight, one correct-by-accident — and neither was detectable by
reading the schema, because nothing recorded which tables are supposed to sync independently.
Every table belongs to exactly one of four classes.

| Class | Carries `‹sync›` | Meaning |
|---|---|---|
| **Root** | yes | Resolved independently, last-write-wins per row by `updated_at` ([02 §7](02-architecture.md)) |
| **Dependent** | no | Travels inside its root's sync payload; never resolved on its own |
| **Reference** | no | Seeded, identical for everyone, shipped with the app and the migration |
| **Derived** | no | A rebuildable cache. Never crosses the wire |
| **Local-only** | no | Exists on the device and nowhere else |

**Roots** — `users`, `subscriptions`, `body_weight_log`, `hr_zone_overrides`, `privacy_zones`,
`exercises`, `routines`, `routine_exercises`, `workouts`, `workout_exercises`, `set_logs`,
`progression_rules`, `mesocycles`, `microcycles`, `planned_sessions`, `planned_exercises`,
`planned_sets`, `cardio_activities`, `activity_segments`, `cardio_plans`,
`cardio_plan_microcycles`, `planned_cardio_sessions`, `xp_awards`, `user_achievements`,
`adherence_streaks`.

A root or dependent under a user-owned root carries `user_id` all the same (§ Conventions): sync class
decides whether a table has `‹sync›`, never whether it has an owner.

**Dependents** — `exercise_secondary_muscles` (of `exercises`), `activity_streams` (of
`cardio_activities`, and uploaded to their own endpoint per [ADR-003](decisions/ADR-003.md)),
`cardio_plan_cycle_targets` (of `cardio_plan_microcycles`).

**Reference** — `muscle_groups`, `modality_increments`, `sport_profiles`, `gamification_tracks`,
`achievements`.

**Derived** — `personal_records` (folds `set_logs`), `user_track_progress` (folds `xp_awards`).

> **A cache is never a sync root. Its ledger is.**
>
> Both derived tables are pure folds over a table that *does* sync, so every device can compute
> them for itself. Syncing the fold as well would create a second, weaker source of truth for the
> same fact — and under last-write-wins a stale device could overwrite a fresher total with an
> older one. It would self-heal on the next rebuild, which is precisely the point: a value that has
> to heal should not have been replicated.
>
> This is the rule that tells you what to do with the next cache somebody adds.

**Local-only** — `raw_gps_points`, `outbox`, `sync_state` (§8), plus the server-only
`refresh_tokens`, `password_reset_tokens`, `email_verification_tokens` and `account_deletion_tokens` (task 019),
which are auth state
rather than user data and never sync anywhere, and `rate_limit_buckets`, which holds nobody's data at
all and so has no owner and no row-level security ([ADR-015](decisions/ADR-015.md)).

### The carve-out that makes plan data different

Roots under `mesocycles` and `cardio_plans` are resolved at **microcycle granularity**, not per
row ([02 §7](02-architecture.md), [ADR-002](decisions/ADR-002.md)): the newer microcycle wins
whole, children included, so a cycle is never assembled half from each device. They are roots for
addressing and idempotence (INV-16); they are not independently *resolved*.

**And "newer" is not only a timestamp.** A microcycle's `engine_version` and `last_write_kind`
decide first: a higher engine version beats a lower one, a user write beats an engine write, and only
two writes of the same kind and version fall back to `updated_at` ([02 §7](02-architecture.md)).
Without this, devices on different engine versions overwrite each other's projections on every
reconciliation — the sync thrash INV-10 exists to rule out ([ADR-004](decisions/ADR-004.md)).

### Enforce it

The Alembic↔Drizzle comparison script in [task 002](tasks/002-database.md) also asserts, from
this table: every root has all four sync columns and — if user-owned — a `user_id` index; no
dependent, reference, derived or local-only table has any of them. `created_at` alone is the exception:
the token tables keep it as an ordinary timestamp, so the check looks for `updated_at`, `deleted_at` and
`sync_version`. Twenty lines, and this entire
class of oversight becomes a CI failure rather than something caught in review two years later.

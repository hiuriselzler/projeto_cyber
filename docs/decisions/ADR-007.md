# ADR-007 — Privacy zones sync as ciphertext under a key the server never stores

- **Status:** Accepted
- **Date:** 2026-09-08 · amended 2026-09-11
- **Related:** [ADR-001](ADR-001.md), [ADR-003](ADR-003.md), INV-15, INV-26,
  [04 §6](../04-security-and-auth.md), [03 §1](../03-database-schema.md)

> **Amendment (2026-09-11) — the claim, stated exactly.** This ADR was titled "ciphertext the server
> cannot read". That is true of **everything the server stores** and false of **the server while it
> runs**: the API receives the user's password at login, and with `privacy_key_salt` and
> `wrapped_privacy_key` whoever controls the running API at that moment can derive the wrapping key
> and open that user's zones.
>
> - **Protected:** database dumps, backups, replicas, anyone with SQL access, support staff, and any
>   request for stored data. A complete copy of what we store contains nobody's home address.
> - **Not protected:** a compromised running API, for users who type their password while it is
>   compromised; and a malicious app build, which no client-side scheme can defend against. The window
>   is narrower than it sounds — the password is sent only at **registration, sign-in on a new
>   device, and password change**; everyday use runs on refresh tokens
>   ([04 §3](../04-security-and-auth.md)) and never sends it.
> - **Considered and declined for v1:** keeping the password off the server entirely, with a
>   client-derived login credential or a PAKE such as OPAQUE. It would make the original claim true,
>   at the cost of moving the breach-list check onto the phone, an enumeration-safe salt lookup before
>   every login, and a redesigned reset flow (§ Revisit if).
>
> The amendment also settles two things the original left open, both in § Decision: **the wrapping
> KDF's parameters**, and **where client-side crypto lives**.

## Context

[04 §6](../04-security-and-auth.md) has required privacy zones since it was written: circles the
user draws around home and work, with any track that starts or ends inside one **trimmed on the
device before upload**. The stated reason for trimming on-device is explicit and correct —
*"server-side masking would mean the server already holds the address."*

Nothing ever said where a zone is stored. It was required by [04 §6](../04-security-and-auth.md),
made permanently free at every tier by INV-26 and [09 §1](../09-business-model.md), given an
acceptance criterion in [task 007](../tasks/007-cardio-recording.md), and onboarded into by
[task 012](../tasks/012-onboarding.md) — and it had no table in
[03-database-schema.md](../03-database-schema.md). The omission was not noticed because the
feature reads naturally as device-local: trimming happens on the device, so the zone lives on the
device, so there is nothing to model.

That reading is wrong, and the way it is wrong is the reason this ADR exists.

## The two requirements, which genuinely conflict

**A zone must reach every device the user owns.** This is a multi-device product
([ADR-001](ADR-001.md)) — a phone and a tablet, or simply a new phone. A second device with no
zones records a run from the same front door and uploads the untrimmed trace. The user did
everything right, once, on the other device. The leak arrives silently, months later, from the
device they forgot they had, and nothing in the product ever tells them it happened.

**A zone must not be readable by the server.** A stored zone is not an approximation of a home
address, it *is* one — a labelled point with a radius, pre-computed, sitting in a table called
`privacy_zones` next to a column called `label`. A trace merely implies where somebody lives and
requires work to exploit; a zone answers the question directly, for every user at once, in a
single `SELECT`. Storing it in plaintext concedes exactly what
[04 §6](../04-security-and-auth.md) refuses to concede to server-side masking, and it concedes it
in a more convenient format for whoever gets the dump.

Assets are ranked in [04 §1](../04-security-and-auth.md) and GPS/home location is first, above
credentials. This is that asset.

## Options considered

**A. Device-local only.** No table, no sync, nothing to leak server-side. This is the reading the
documents accidentally implied. Rejected: it fails the first requirement completely and fails it
*invisibly*, which is the worst property a privacy control can have. A safety feature whose
failure mode is silent is not a safety feature.

**B. Plaintext server-side.** One ordinary synced table. Simple, debuggable, and what Strava does.
Rejected: it fails the second requirement, and it does so while
[04 §6](../04-security-and-auth.md) still contains a paragraph explaining why we will not do the
structurally identical thing for masking. Shipping B would mean that paragraph is decoration.

**C. Sync the zone as ciphertext under a key the server never stores.** Both requirements hold. The
cost is key management and one genuinely lost capability (§Consequences).

**D. Derive zones on-device from history** (cluster common start points, trim automatically). No
storage question at all, and no user effort. Rejected as a *replacement* — it is a heuristic making
an irreversible privacy decision on the user's behalf, it cannot express "my parents' house", and
its failures are exactly as silent as option A's. Worth revisiting one day as a **suggestion** that
the user confirms into a real zone, never as the mechanism.

## Decision

**Option C.**

```
32-byte privacy key
    ├─ generated on-device at registration (OS CSPRNG), stored in expo-secure-store
    ├─ wrapped with argon2id(password, privacy_key_salt, m=64 MiB, t=3, p=1)   ← derived CLIENT-side
    │      salt distinct from the login password hash's; cost never below the login hash's
    └─ users.wrapped_privacy_key + privacy_key_salt + privacy_key_kdf stored server-side

privacy_zones row = XChaCha20-Poly1305(
      {label, center_lat, center_lng, radius_m},  key = privacy key,  fresh nonce
)
```

- A new device unwraps the key with the password the user has **just typed to sign in**. No extra
  step, no code to transcribe, no second factor to lose.
- The server stores an id, a user id, a blob and a nonce. Not the label, not the radius — a 200 m
  circle and a 2 km circle say different things about what is being hidden.
- Changing the password re-wraps the key. It does not re-encrypt the zones.
- **The wrapping KDF is never cheaper than the login hash.** `wrapped_privacy_key` is an
  authenticated ciphertext, so anyone holding a dump can test a password guess against it — it is a
  password-verification oracle exactly like `password_hash`. An attacker attacks whichever is cheaper,
  so a weak client-side KDF would lower the cost of cracking **the password itself**, not only the
  zones. The rule: the client KDF's memory and iterations are each **at least** those of the server's
  login hash ([04 §2](../04-security-and-auth.md): 64 MiB, `t=3`). v1 uses argon2id **`m=64 MiB`,
  `t=3`, `p=1`** — parallelism does not change an attacker's per-guess cost, and libsodium's argon2id
  is single-lane. The parameters are stored beside the wrap in `users.privacy_key_kdf`, so they can be
  raised on the next password entry without a migration, and a test fails if the client constants
  ever fall below the server's.
- **Client-side crypto lives in `apps/mobile/src/crypto/`**, the only folder that may import the
  crypto library or read the privacy key from `expo-secure-store`
  ([responsibility-map](../responsibility-map.md)). It uses **libsodium through a native binding**
  (candidate: `react-native-libsodium`, confirmed in [task 003](../tasks/003-authentication.md)):
  argon2id, XChaCha20-Poly1305, and the OS CSPRNG for keys and nonces. **Not in `core-rs`:** the core
  bans randomness (INV-10), the server never decrypts so a shared implementation buys nothing, and
  privacy zones must not depend on the ADR-004 spike's outcome. **Not pure JavaScript:** argon2id at
  64 MiB takes seconds in Hermes, which is exactly the pressure that produces a weak KDF.
- On-device the zones are stored **decrypted** ([03 §8](../03-database-schema.md)). The phone
  already holds `raw_gps_points`; encrypting the zone beside them would protect nothing, and the
  trimmer needs plain values on every finish.
- Trimming remains exactly where [04 §6](../04-security-and-auth.md) already put it: on the
  device, before upload. **This ADR does not move the trimming.** It only answers where the zone
  itself lives.

## Consequences

**Good**
- Both requirements hold simultaneously, which options A and B each fail in one direction.
- A database breach yields no addresses. That is a categorical difference from option B, not a
  degree of hardening.
- It keeps [04 §6](../04-security-and-auth.md)'s existing argument honest. The document already
  refuses to let the server hold the address; this is that refusal applied to the one table that
  would otherwise have contained it.
- The blob is opaque to the sync protocol, so it needs no special handling — an ordinary root row
  ([03 §11](../03-database-schema.md)) that happens to be unreadable.

**Bad — accepted**
- **A password reset destroys the zones.** Nothing the server stores can unwrap the key without the
  password. The user is told at reset time, before committing, and re-draws them.

  This is the consequence most likely to be argued away later, so it is worth stating plainly: it
  is not a flaw in the design, it *is* the design. A reset that could recover the zones would mean
  the server could read them all along, which is option B wearing a costume. The cost is a few
  minutes of a user's time; the property bought is that a dump of our database contains nobody's
  home address.
- No server-side support tooling can ever inspect a zone, so "my zone isn't trimming" is debugged
  from the device or from the user's description. Consistent with
  [04 §12](../04-security-and-auth.md), which already rules out back-office reads of training data.
- **A compromised running API could open zones** for users who type their password while it is
  compromised (§ Amendment). Accepted for v1: the stored data — what breaches, backups and replicas
  expose — stays unreadable.
- Client-side argon2id at 64 MiB is slower on a phone than the server's hash — on the order of a
  second on a mid-range Android device, measured in [task 003](../tasks/003-authentication.md). It runs
  only at registration, new-device sign-in and password change, never on an ordinary launch, and the
  screen shows progress rather than freezing.
- **One more native module.** libsodium through a native binding means a fix to it is a store release,
  not an OTA update.
- One more piece of crypto in a solo project. Mitigated by keeping it to a single well-trodden
  construction with no bespoke protocol: derive, wrap, seal, open.

## Revisit if

- **The threat model comes to include a compromised running API** — for instance when the Coach tier
  or a support tool widens who operates it or can reach it. Then keep the password off the server (a
  client-derived login credential or OPAQUE), which is what makes the original title's claim true.
- Zone loss on password reset turns out to be a real support burden. The answer is a
  **user-held** recovery code shown once at zone creation and included in the data export
  ([04 §7](../04-security-and-auth.md)) — never a server-held escrow, which would reintroduce
  option B by the back door.
- The Coach tier ([task 015](../tasks/015-coach-tier.md)) needs an athlete to share location with
  a coach. That is a different problem — sharing a *trace* under consent, not sharing a zone — and
  it gets its own security review, as [09 §3](../09-business-model.md) already requires.

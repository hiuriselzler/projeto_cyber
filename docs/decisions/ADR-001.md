# ADR-001 — The phone owns a full local database; the server is a sync target

- **Status:** Accepted
- **Date:** 2026-09-07
- **Supersedes / superseded by:** —
- **Related:** [ADR-002](ADR-002.md), INV-09, INV-16, NFR-1, NFR-8

## Context

The user chose a custom backend: FastAPI + PostgreSQL. That is a good choice for owning the data
and for the relational modelling the progression planner needs.

It collides with a physical fact: **gyms have no signal.** Basements, thick walls, underground
car parks. So do trail runs, and so do long stretches of any ride. The two places this app is
used are the two places a phone has no connectivity.

Meanwhile the interaction budget between sets is about three seconds (NFR-2), and losing a
logged workout is the worst failure the app can have (NFR-8) — worse than a crash, worse than
being wrong, because the data existed nowhere else and the training session cannot be repeated.

So: where does a set live the moment the user taps ✓?

## Options considered

**A. Online CRUD with a loading spinner.** The client POSTs each mutation; the server is the
source of truth. Simple, one implementation of everything, trivially consistent.
Fails outright — the app is unusable exactly where it is used.

**B. Optimistic UI over a request cache.** TanStack Query with an offline mutation queue and a
persisted cache. Cheap, familiar, and roughly what most apps do.
The cache is a cache: it is not designed to be authoritative, has no schema, cannot be queried
relationally (volume per muscle group per microcycle is a four-table join — [03 §9](../03-database-schema.md)),
and eviction is not something to bet an irreplaceable workout on. It works right up until it
loses something.

**C. Local SQLite as the working copy, server as the durable shared copy.** The client has the
full relational schema. Every read and write is local and synchronous. A background outbox
reconciles with the server.

**D. Drop the custom backend for a sync-native platform** (Firestore, PowerSync, ElectricSQL).
Solves sync for us, genuinely well. Rejected because the user explicitly chose a custom backend,
and because the progression engine wants real relational modelling and server-side computation.
Worth naming, though: **PowerSync or ElectricSQL sitting in front of our own Postgres is the
serious alternative to hand-writing §Consequences' sync protocol**, and is the first thing to
reconsider if sync bugs dominate development time.

## Decision

**Option C.**

- The mobile app carries the full schema in SQLite (`expo-sqlite` + Drizzle), minus auth and
  derived tables ([03 §8](../03-database-schema.md)).
- Every UI read and write hits local SQLite. **No network call is ever on the path of logging a
  set** (NFR-2), and an in-progress workout is a database row, not component state (INV-09).
- Mutations append to an `outbox` table; a background worker drains it into `POST /sync/push`
  with exponential backoff. Sync failure is invisible unless it persists.
- **All user-data primary keys are UUIDv7 minted by the creating device** (INV-16). The server
  never allocates an ID for user data.

That last point is what makes the whole thing work. Because the client owns the ID:

- a workout created offline has its permanent identity immediately, so its exercises and sets can
  reference it before it has ever been seen by a server;
- `sync/push` is an **upsert keyed on a client ID**, so retrying a batch is idempotent by
  construction — no dedup logic, no idempotency-key table, no "did that succeed?" ambiguity
  after a timeout;
- two devices can create rows concurrently without coordination.

UUIDv7 rather than v4 because it is time-ordered, which keeps B-tree index locality reasonable
and makes `ORDER BY id` a sane fallback.

## Consequences

**Good**
- The app works fully offline, forever, including planning ahead and reviewing history.
- Logging is instant because it is a local write.
- A backend outage is invisible to the user ([05 §10](../05-integrations.md)).
- Every device is an incidental extra copy of the data.

**Bad — accepted deliberately**
- **We are writing a sync protocol.** This is the hardest part of the project and where the
  subtle bugs will be. Budgeted as its own task, not smuggled into feature work.
- Two schemas and two migration streams to keep compatible ([06 §4](../06-operations.md)).
- A device can be many app versions behind, so the server must tolerate old clients and the sync
  protocol must ignore unknown fields in both directions.
- Conflict resolution is a product decision, not just a technical one. Policy: last-write-wins
  per row, except that **a set or an activity present on either side is never dropped** (NFR-4).
  Losing a duplicate is annoying; losing a set is unacceptable.
- Client-minted IDs mean the client picks the identifier — so every write still gets a
  server-side ownership check (INV-15). Choosing an ID is not choosing an owner.

**The most dangerous consequence**, called out because it is easy to miss: a local migration that
fails on a device holding an un-synced workout destroys data that exists nowhere else. Hence the
rule in [06 §4](../06-operations.md) — back up the SQLite file before migrating whenever the
outbox is non-empty, and never ship a local migration over OTA.

## Revisit if

- Sync bugs consume more development time than features. Then adopt PowerSync or ElectricSQL over
  the existing Postgres (option D-hybrid) — the schema is already designed for it.
- Real-time multi-device collaboration becomes a requirement (it is not; there is no coach
  feature in v1).

# ADR-009 — Android first; iOS as a structural addition, not a port

- **Status:** Accepted
- **Date:** 2026-09-10
- **Related:** [ADR-004](ADR-004.md), INV-19, INV-28, [09 §2](../09-business-model.md),
  [task 001](../tasks/001-project-bootstrap.md), [task 016](../tasks/016-ios-platform.md),
  [ADR-012](ADR-012.md)

> **Amendment (2026-09-11, [ADR-012](ADR-012.md)).** The `core-rs` native module is **not** loaded in
> `src/platform/`: its binding is a workspace package imported only by `src/domain/`, because an
> autolinked native module needs no OS-specific code to load. If the ADR-004 spike shows a loading step
> that differs by OS, that step alone moves into `src/platform/`. The shared folders that never know the
> OS also include `src/crypto/` ([ADR-007](ADR-007.md)) and `src/account/` (ADR-012), as INV-28 lists.

## Context

The stack was specified as "React Native + Expo, iOS + Android", and two facts collided with it.

**The developer works on Windows.** iOS native builds need Apple's toolchain: Xcode runs only on
macOS, and Rust cannot be compiled for iOS without Apple's SDK and linker. From Windows, every iOS
iteration is a remote cloud build of roughly 15–30 minutes, and a development build on a physical
iPhone needs a paid Apple Developer membership from the first day.

**ADR-004's spike assumed both platforms within two days.** It required calling the Rust core from a
physical iOS device and a physical Android device inside a hard timebox. From this machine, the iOS
half would have been decided by build-queue waits rather than by whether the toolchain works — the
spike would have measured patience, not the question.

And a market fact makes Android-first more than a workaround. **The first paying market is Brazil**
([09 §2](../09-business-model.md)), where roughly four in five smartphones run Android.

## Options considered

**A. Both platforms from day one — the status quo.** Needs a Mac or remote builds throughout; puts the
spike's iOS half at the mercy of a build queue; doubles the device matrix during the heaviest
development.

**B. Android only, with no provision for iOS.** Fastest today. Rejected: Android assumptions accumulate
silently in shared code while nothing exercises an alternative, and the eventual iOS work becomes a
port — finding, by hand, every place that assumed the operating system.

**C. Android first, iOS as a planned addition, with the structure for it enforced from the first
commit.** Chosen.

## Decision

- **Initial development and the first release target Android only.** iOS is
  [task 016](../tasks/016-ios-platform.md), after the Android launch.
- **The operating system is known in exactly one place: `apps/mobile/src/platform/`** (INV-28). Every
  difference between Android and iOS — background-location service configuration, notification
  channels, haptics, store specifics behind the billing layer — lives there or in the Expo config
  plugins, behind interfaces the rest of the app calls without knowing which OS answers. `features/`,
  `account/`, `domain/`, `db/`, `sync/`, `recording/`, `crypto/` and `ui/` never branch on the platform.
- **Enforced by lint, not by memory.** A rule rejects `Platform.OS`, `Platform.select` and
  `.android.*` / `.ios.*` files outside `src/platform/`. This matters most *because* there is only one
  platform: with no second OS to break, an Android assumption in shared code fails nothing and would
  otherwise go unnoticed until the port.
- **What is already platform-neutral stays that way.** The schema and sync protocol
  (`subscriptions.store` keeps its `apple` value), the API, the pure domain core, `expo-secure-store`,
  `react-native-maps` with native providers, local notifications, the design tokens — and
  **RevenueCat**, which is used from day one partly *because* it makes iOS a second store rather than
  a second billing integration.
- **ADR-004's spike runs on a physical Android device.** Its outcome decides the core for Android and
  the server. **The iOS half is moved, not dropped: it is the first gate of task 016**, before any iOS
  feature work.
- **Accessibility and scaling targets are stated in Android terms for now** — TalkBack, system font
  scale to 200 % — with VoiceOver and Dynamic Type as acceptance criteria of task 016.

## Consequences

**Good**
- **Windows is a fully supported development machine.** Android Studio, the Android NDK and
  `cargo-ndk` all run on it; nothing in tasks 001–015 needs a Mac.
- The Rust spike tests the toolchain, not build-queue patience.
- One device matrix during the heaviest development.
- The first market is served on the platform most of its users carry.
- The structure is checked against its own rule by CI from the first commit, and task 016 carries the
  proof: **if adding iOS requires editing shared code, the structure failed** — the same shape of test
  as "adding `walk` is a profile row" in task 007.

**Bad — accepted**
- **The US half of the business model is materially weaker until iOS ships.** iOS is the majority
  platform in the United States, and historically where app subscription spend concentrates. The
  prices in [09 §2](../09-business-model.md) still stand; US revenue expectations should not be read
  from them until task 016 is done.
- **The iOS half of the Rust question is deferred, not answered.** If UniFFI's React Native bindings
  prove hostile on iOS, the iOS app cannot use the core as built, and the fallback is option A *for iOS
  alone* — a TypeScript mirror of the engine, policed by the shared fixtures, reintroducing on one
  platform, late, the duplication [ADR-004](ADR-004.md) exists to remove. UniFFI's iOS path is mature
  in native Swift apps; its React Native bindings are newer, and nothing about them is verified on this
  project. **This is the most expensive thing this ADR defers, and it is deferred knowingly.**
- App Store requirements that Android does not have — background-location justification in review,
  privacy nutrition labels — surface in task 016 rather than earlier.
- Anyone who wants the app on an iPhone waits, and store listings and marketing are Android-only at
  first.
- The founding-price window ([09 §2](../09-business-model.md)) opens at the Android launch and **does not
  reopen for iOS** (decided 2026-09-11). iPhone users arriving later are offered the standard price.

## Revisit if

- **A Mac becomes available.** Pulling the iOS half of the ADR-004 spike forward is then cheap, and it
  retires the largest risk this ADR defers.
- The US market turns out to matter more, sooner, than Brazil.
- Task 016's first gate fails.

# ADR-010 — Exact numbers: bodyweight e1RM, per-set RIR, percentages, the safety rail and the XP curve

- **Status:** Accepted
- **Date:** 2026-09-11
- **Related:** INV-02, INV-05, INV-07, INV-10, INV-22, INV-25, INV-26, [ADR-004](ADR-004.md),
  [01 §3, §6](../01-business-requirements.md), [08 §2](../08-gamification.md)

> **Amendment (2026-09-11) — loads, rounding modes and ties.** The principle below makes every number
> client and server agree on either exact or frozen. Loads are neither, and this amendment says why that
> is acceptable and what keeps it safe.
>
> - **A load crosses the core as `f64` kilograms**, and so does an increment. Storage is unchanged:
>   `numeric(9,4)` loads and `numeric(10,6)` increments in Postgres (INV-02), a double in SQLite.
> - **Why no integer representation is needed.** Agreement on a load is agreement on *which step of the
>   grid* it is, not on its last decimal. `round_to_increment()` re-anchors every prescribed load to an
>   exact multiple of its increment from whatever value it is given, so storage rounding in either
>   database cannot move a load onto a different step — the property INV-02's 52-cycle simulation already
>   demonstrates. The function uses only division, multiplication, `floor` and `ceil`, which IEEE-754
>   defines exactly; no powers, no logarithms.
> - **Three modes:** `nearest`, `down` and `up`.
> - **A tie goes to the lighter load.** A value exactly halfway between two steps — 41.25 kg on a 2.5 kg
>   grid — rounds to **40 kg** under `nearest`. This is the direction the safety rail already rounds
>   (§4): when the arithmetic cannot decide, the engine never prescribes more than the rule asked for.
> - **Ties are implemented explicitly, never with a language's `round()`.** Python's `round()` sends a
>   half to the even neighbour and JavaScript's `Math.round()` sends it upward; neither is this rule. The
>   rule is `steps = floor(q)`, plus one only if `q − floor(q) > 0.5`, where `q = weight / increment`.
>   It matters most if ADR-004's spike yields option A, where two implementations must agree on exactly
>   the tie case.
> - `invariants.md` is not changed: INV-02 already names `round_to_increment()` as the only rounding, and
>   its modes and tie rule are that function's specification, carried in
>   [01 §3.2](../01-business-requirements.md) and [task 005](../tasks/005-strength-progression-planner.md).

## Context

Five rules the engine needs were either unspecified or specified in a way that could not work. They
are settled together because four of them fail in the same way: **a number the client and the server
must agree on, held in a form that cannot be exact.**

- **Bodyweight exercises had no e1RM rule.** INV-07's formula takes `weight_kg`, which for a weighted
  pull-up is the belt, not the lifter. Bodyweight *volume* had already been settled as body weight
  plus added load ([01 § Answered](../01-business-requirements.md)); e1RM had not.
- **Per-set RIR targets had no stated relationship to the RIR bounds.** `rir_mode: per_set`
  (FR-3.8a) allows a ladder, INV-05 bounds every generated RIR, and nothing said how the two combine.
- **Every percentage column was a fraction at two decimal places.** 2.5 % cannot be stored: Postgres
  rounds `0.025` in a `numeric(5,2)` to `0.03`. A 2.5 % step on a 140 kg squat would therefore
  prescribe **145 kg instead of 142.5 kg**. A 7.5 % cardio step and a 92.5 % back-off load fail the same
  way, and `load_step_pct` had no stated convention at all.
- **The cardio safety rail failed on its own default plan.** The stored rail, `0.0136`, is
  `ln(1.10)/7 = 0.013616` rounded *down* — so the documented default step of +10 % per 7-day cycle
  already exceeds it, as do the rounded defaults for 10-, 12- and 14-day cycles. The documents also
  never said whether the rail compares a step simply (step ÷ days) or compounded, and the two give
  different verdicts. A rail that fires on the default plan is a rail users learn to dismiss — and
  FR-6.5a is an injury-prevention feature that INV-26 keeps free at every tier.
- **The XP curve did not exist.** "Level 1–30, on a curve that flattens deliberately" was the whole
  specification, for a function INV-22 now constrains: a steeper curve would lower levels, which is
  forbidden.

## The principle the numeric decisions share

**Every number that client and server must agree on is exact in every layer** — Postgres, SQLite,
Rust, Python and TypeScript — **or it is computed once, rounded on the safe side, and frozen as an
integer table that ships as the source of truth.**

TypeScript has no decimal type, SQLite stores `numeric` as a double, and a value produced by a power
or a logarithm can land a hair either side of a boundary depending on the runtime. ADR-004 already
warned that two implementations of a rounding rule "will eventually disagree on a float boundary".
Integers do not.

## Decision

### 1. e1RM for bodyweight exercises (INV-07)

For an exercise with `uses_bodyweight`, the load in the e1RM formula is **body weight plus added
load**. The body weight is **the latest `body_weight_log` entry on or before the set's `local_date`** —
never the user's current body weight, or every historical pull-up's e1RM would change each time they
weigh in (INV-17). With no entry by that date, e1RM is NULL, exactly as it is for a set logged without
RIR: no guess. Tonnage uses the same lookup, and `max_weight` and `best_e1rm` PRs compare total load,
displayed as "BW + 20 kg".

### 2. Per-set RIR is a sum, clamped (FR-3.8a, INV-05)

Under `rir_mode: per_set`, each working set's target RIR is **the exercise's target RIR plus that set's
offset**. The engine progresses one number, the target; the offsets are a ladder the user authors once
(`progression_rules.rir_offsets`, for example `[2, 1, 0]`). **Every sum is kept inside
`[min_rir, max_rir]`**: an out-of-range sum is clamped, and the set is marked `was_clamped`, so the plan
can say why a set reads RIR 3 rather than 5. INV-05 is unchanged — the engine still never generates a
set outside its rule's bounds.

### 3. Percentages are integer basis points (INV-10)

Every percentage becomes an integer column named with its unit, the way INV-01 names kilograms:
`load_step_bp` (250 = 2.5 %), `failure_load_bp`, `deload_set_bp`, `deload_load_bp`, `volume_step_bp`,
`deload_volume_bp`, and `percent_wave_bp` as an integer array (`[7000, 7500, 8000]`). A load derived
from a percentage is immediately re-anchored by `round_to_increment()` (INV-02), so the one
non-integer step in the chain returns straight to an exact grid.

### 4. The safety rail is a frozen table (FR-6.5b, INV-25)

The rule is the one the documents' own numbers already implied: **+10 % per 7 days, compounded** — a
cycle of `n` days may raise volume by at most `1.10^(n/7) − 1`. That value is irrational for almost
every `n`, so it is **computed once for n = 1 … 28, rounded down to whole basis points, and frozen** as
a table in the domain core. The check is an exact integer comparison:
`volume_step_bp ≤ RAIL_BP[length_days]`.

The default step for a cycle *is* the table's value, so **a default plan passes its own rail by
construction** — the 7-day entry is exactly 1000 bp. The rail can still be switched off for a plan by a
deliberate, recorded user action (`rail_overridden_at`), as FR-6.5 requires. It is never relaxed by
rounding.

The table is generated once and committed, never recomputed at runtime: recomputed, the 7-day value can
come out as 999 on one platform and 1000 on another. Changing the table changes projections, so it
bumps `ENGINE_VERSION` ([ADR-004](ADR-004.md)).

### 5. The XP curve is a frozen table, started steep (08 §2, INV-22)

**The curve can only ever get cheaper.** INV-22 forbids lowering anyone's level, so any change must be
level-preserving or level-raising for every existing user. A curve launched too easy is therefore
permanent; one launched slightly hard can be loosened on evidence. So the curve starts at the demanding
end of reasonable — while keeping the first levels fast, because that is where motivation is won or
lost.

It was designed as `XP to reach level L = 12 × (L − 1)^2.7`, rounded to the nearest 10, and is
**frozen as a 30-row integer table**. The table runs, not the formula, so a phone and a server can never
disagree about a level because of a floating-point power. For someone completing four prescribed
sessions a week (about 400 XP a week on that track): level 2 after the first session, level 5 in about
nine days, level 10 in under three months, level 20 in about a year and a half, and each level past 25
taking four to five months. Level 30 is roughly a five-year aspiration, deliberately — there is no
level-cap race to run.

Each track carries `level_scale_bp` (default 10 000), which multiplies its thresholds in integer
arithmetic, so a slow-earning quality track can be loosened without loosening the rest. It may only
ever decrease.

## Consequences

**Good**
- Five numbers the engine depends on are defined before any of it exists, and every one is exact in
  every layer.
- The safety rail stops contradicting its own default, and its check needs no tolerance.
- A 2.5 % load step means 2.5 %.
- A bodyweight lifter's e1RM history is stable when they weigh in.
- Early levels come quickly, and the curve has room to loosen on real data without ever breaking
  INV-22.

**Bad — accepted**
- **Seven percentage columns are renamed** and one JSON array changes shape. Free now, before task 002;
  expensive afterwards.
- **A bodyweight lifter who never logs body weight gets no e1RM** for those exercises. It is the same
  deliberate incentive as a missing RIR under INV-07 — stated once, plainly, never nagged.
- **A ladder wider than its bounds is flattened** until the user widens them. `was_clamped` makes that
  visible rather than silent.
- **Frozen tables need their own change discipline.** A rail-table change bumps `ENGINE_VERSION`; an
  XP-table change must pass the level-preserving replay check (task 013). Neither can be edited
  casually — which is the point.
- **The steep start may feel slow to some users in the first months.** The response is to loosen the
  curve on evidence, which is always permitted. The reverse never is.

## Revisit if

- Real ledgers show a quality track stalling for users who follow their plans: lower that track's
  `level_scale_bp`.
- The 10 %-per-week ramp proves wrong for a particular sport — swimming volume tolerates different
  ramps from running. The answer is a per-sport rail table, not a looser shared one.

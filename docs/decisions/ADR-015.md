# ADR-015 — Account security in practice: rate limits in Postgres, a rotation grace window, and a bundled breach list

- **Status:** Accepted
- **Date:** 2026-09-14
- **Related:** INV-15, NFR-1, NFR-10, NFR-12, [ADR-001](ADR-001.md), [ADR-007](ADR-007.md), [ADR-011](ADR-011.md),
  [04 §2, §2a, §3, §5](../04-security-and-auth.md), [03 §1, §11](../03-database-schema.md),
  [task 003](../tasks/003-authentication.md)

## Context

Planning [task 003](../tasks/003-authentication.md) against [04](../04-security-and-auth.md) found four places where the
security document states a requirement and leaves out the mechanism — or where the mechanism as written defeats another
requirement.

**1. Rate-limit counters had nowhere to live.** [04 §5](../04-security-and-auth.md) and NFR-12 require the counters in
shared storage, never in process memory, so a limit holds across more than one API instance. The stack has no shared
store but Postgres: no document, compose file or CI job mentions Redis or anything like it.

**2. Strict refresh-token reuse detection signs out people who did nothing wrong.** Rotation is a write the server
commits before the client has the new token. If the request times out, the network drops or the app is killed after the
server rotates but before the new token reaches secure storage, the client's next refresh presents the replaced token.
[04 §3](../04-security-and-auth.md) reads that as theft: the device's whole chain is revoked and the user is told a token
was stolen. In an offline-first app used in gyms (NFR-1), a dropped response is ordinary. The cost is a signed-out user
who must type their password again — which is also one more time the password reaches the server
([ADR-007 § Amendment](ADR-007.md)) — and a security alert that teaches people to ignore security alerts.

**3. The breach-list check could not be built as written.** "A local breach list (k-anonymity offline set)" names two
different things. k-anonymity is the property of Have I Been Pwned's *online* range API, which 04 §2 rightly refuses to
call; an offline set needs no k-anonymity, and the complete Pwned Passwords corpus is tens of gigabytes.

**4. Registration reveals whether an email has an account.** 04 guards login and the reset request against enumeration
and says nothing about registration, where a duplicate address has to fail somehow.

## Options considered

### Rate-limit storage

**A. Redis or a managed equivalent.** The conventional choice, with an atomic increment and expiry built in. Rejected
for v1: a second stateful service in every environment — compose, CI, a managed provider, its own monitoring — to hold
a few counters, while Postgres is already on the path of every request a limit protects.

**B. A counter table behind a `SECURITY DEFINER` function**, with no table grants to the app role. It keeps
[ADR-011](ADR-011.md)'s "every unscoped read is a named function" literal. Rejected: that allowlist exists to make
cross-user access to *user data* visible and rare. Spending an entry on a table holding nobody's data dilutes what the
list means, and moves it toward its ten-entry revisit threshold without protecting anything.

**C. A plain Postgres table holding no user data, written by one atomic upsert.** **Chosen.**

### Refresh reuse against a lost response

**A. Strict, as 04 §3 was written.** Rejected: context 2.

**B. Keep a replaced token valid until its successor is first used.** No false alarms at all. Rejected: a device that
rotated and then went offline for weeks — ordinary here — would leave its previous token redeemable for weeks, and a
thief holding it would not be detected until the device came back.

**C. A short grace window:** a replaced token is accepted once more only while its successor is unused and less than
60 seconds old. **Chosen.** It covers the retry after a timeout and an immediate relaunch, which are the common cases,
and it bounds how long a stolen token can go unnoticed.

### Breach list

**A. The Have I Been Pwned range API at registration.** Already refused by 04 §2: it sends a password-hash prefix to a
third party, and registration would depend on its availability.

**B. The full Pwned Passwords corpus, offline.** Rejected: tens of gigabytes in a container, for a check whose value is
concentrated in the most common entries.

**C. A bundled list of the most common breached passwords, cut to what the length rule still admits.** **Chosen.**

### Registration enumeration

**A. An identical response for new and existing addresses**, with an email to the existing owner. Rejected for v1:
registration has to hand back a session at once, so a new user can train offline straight away (FR-1.1b, NFR-10). An
identical response means either a fake session or registration completed by an email link, and either breaks the
three-minute first set.

**B. Disclose it, behind the registration rate limit.** **Chosen.**

## Decision

### 1. Rate limits live in Postgres

```sql
rate_limit_buckets (
  bucket_key   text NOT NULL,          -- '<rule>:<ip|account>:<HMAC-SHA256 of the subject>'
  window_start timestamptz NOT NULL,
  hits         integer NOT NULL CHECK (hits > 0),
  PRIMARY KEY (bucket_key, window_start)
)
INDEX (window_start)                    -- the purge
```

- **One statement per hit** — `INSERT … ON CONFLICT DO UPDATE SET hits = hits + 1 RETURNING hits` — atomic across API
  instances and safe under transaction-mode pooling.
- **Fixed windows** of the lengths in [04 §5](../04-security-and-auth.md), counted per IP and per account (the normalised
  email) separately. Whichever trips first answers `429` with `Retry-After` set to the seconds left in its window. A
  fixed window admits up to twice the limit across a boundary; accepted, because these limits are brakes on guessing,
  not quotas.
- **No address and no email is stored.** The subject is an HMAC-SHA256 under a key derived from `JWT_SECRET` with a
  fixed label. Rotating `JWT_SECRET` resets every counter; accepted.
- **Nobody's data, so no owner, no RLS and no sync columns.** The table is classified *local-only*, server-side
  ([03 §11](../03-database-schema.md)), and the app role reads and writes it through ordinary grants. ADR-011 governs
  rows that belong to a user; this table has none. Its one repository says so, like the schema-version repository
  before it.
- Windows older than a day are purged by an ordinary `DELETE` in the maintenance service.

### 2. Refresh rotation has a 60-second grace window

When refresh token `T` is presented:

| `T` is | Then |
|---|---|
| active — not revoked, not replaced, not expired | **Rotate:** issue `S`; set `T.replaced_by = S` and `T.revoked_at = now` |
| replaced by `S`, and `S` is unused (neither replaced nor revoked) and issued less than 60 s ago | **Grace:** issue `S′`; set `S.replaced_by = S′` and `S.revoked_at = now`; answer with `S′`. Not a reuse event |
| replaced, in any other case | **Reuse:** revoke every active token of `T`'s device, send the reuse notification, answer `401` |
| revoked with no successor, expired, or unknown | `401`, and nothing else |

**Detection is delayed, never lost.** A thief who redeems `T` inside the window gets `S′` and retires the legitimate
device's `S`. When that device next presents `S`, it has been replaced, the window has passed or `S′` has been used, and
the chain is revoked — the thief's `S′` with it.

**What the window does not cover:** an app killed while its refresh was in flight and reopened minutes later. That
device is signed out as before. Accepted; see § Revisit if.

### 3. The breach list is the NCSC top 100 000, cut to ten characters

- **Source:** the UK National Cyber Security Centre's list of the 100 000 most common passwords in Pwned Passwords
  (2019). The NCSC no longer serves it; the copy used is SecLists' mirror, under the MIT licence, with its SHA-256
  recorded in the decision log.
- **Only entries a user could choose are kept.** The minimum length is 10 ([04 §2](../04-security-and-auth.md)), which
  leaves 9 307 of 99 840.
- **Stored as sorted SHA-1 digests**, one per line, generated by a script from the verified source — so the repository
  and the container ship no plaintext password list, and the file can be rebuilt and diffed.
- A candidate is rejected if it, or its lower-case form, is on the list — at registration, password change and password
  reset.

### 4. Registration discloses an existing account

`POST /auth/register` with an address already in use answers `409`. It is rate-limited to 5 an hour per IP and per
account key ([04 §5](../04-security-and-auth.md)). Login and the reset request still disclose nothing.

## Consequences

**Good**
- Limits hold across any number of API instances with no new infrastructure, and a database dump reveals no IP address
  or email through them.
- The common lost-response cases no longer sign users out or send them false theft alerts, and theft is still caught.
- The breach check is offline, reproducible and a few hundred kilobytes.

**Bad — accepted**
- **Every limited request writes a row.** Cheap at v1's scale, and the first thing to measure under load (NFR-12, open
  question 6).
- **A stolen refresh token can be redeemed once, unnoticed, for up to 60 seconds** after the legitimate device rotated.
- **Relaunching after a lost rotation still signs the device out** if more than 60 seconds have passed.
- **The breach list is from 2019 and covers the most common passwords only.** It stops the passwords attackers try
  first, not every breached one.
- **An attacker can learn whether an email has an account**, five guesses an hour per IP.
- The per-account limit lets anyone slow a victim's logins to 10 per 15 minutes by failing on purpose. Inherent in 04 §5's
  per-account limit, and a nuisance rather than a lockout.

## Revisit if

- Rate-limit writes show up in database load, or a limit needs sub-second precision — option A, Redis.
- Users report being signed out after a lost refresh — make rotation idempotent: the client stores a random rotation id
  before the request, and a retry carrying the same id receives the same successor.
- A newer or larger common-password list becomes available under a usable licence — it is a data file and a script
  argument, not a code change.
- A second table appears that holds no user's data and is written by the API — state the rule in [ADR-011](ADR-011.md)
  itself.

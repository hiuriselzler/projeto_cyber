# ADR-002 — Plans are materialised rows, re-projected by a pure engine

- **Status:** Accepted
- **Date:** 2026-09-07
- **Related:** [ADR-001](ADR-001.md), INV-05, INV-06, INV-10, FR-3.x

> **Amendment (2026-09-26) — the engine speaks natural keys; the wrappers mint ids.** Every plan row needs a
> client-minted UUIDv7 (INV-16), and the engine may use neither a clock nor randomness (INV-10), so the engine
> cannot mint one. Decided at the start of [task 005](../tasks/005-strength-progression-planner.md):
>
> - **The engine identifies a row by its place in the plan**, never by an id: a microcycle by `cycle_number`, a
>   session by `(day_index, order_index)` within its cycle, an exercise by `order_index` within its session, and a
>   set by `set_index` within its exercise.
> - **The wrappers in `app/domain/` and `src/domain/` mint ids** for the rows `generate` creates, and
>   `reconcile` matches the rows it is given **by natural key**, so a row keeps its id — and with it its
>   `user_edited` origin and its pin (FR-3.14) — through every re-projection.
> - **Weighed and rejected:** handing the engine a pool of pre-minted ids. It keeps the engine pure, but its
>   output would then depend on the pool's order, which is an idempotence hazard (INV-10) bought for nothing.
>
> **The one consequence to watch:** a natural key must not change while the row keeps its meaning. A session
> that no longer fits a shortened cycle is the first case — see task 005's stage 1.

## Context

The planner is the product ([00](../00-project-context.md)). The user's brief:

> "a weekly planning system aimed at progressive overload… Week 1: Squats 3×6 at 40 kg,
> progressing weekly with options for deloads, leading to Week 12: Squats 3×6 at 63 kg,
> including settings for minimum and maximum rep limits."

Three requirements are hiding in that sentence and they pull against each other:

1. **See the future.** Cycle 12 must be visible in cycle 1. That is the whole appeal of a block.
2. **Edit the future.** Change cycle 9's squat because of a holiday, and have the change stick.
3. **React to reality.** If cycle 3 went badly, cycle 4 must not blindly continue the ramp. If it
   went well, it should accelerate. That is the feedback loop competitors lack.

(1) and (3) are in tension. A plan fixed at creation cannot react; a plan computed fresh on every
read cannot be edited or trusted to stay put.

> **Terminology.** The user later established that the repeating unit is a **microcycle** of
> user-chosen length — 5 days, 7, 9, whatever (INV-25). This ADR says "cycle" throughout; the word
> "week" appears only where it means a literal calendar week. The argument is unaffected by cycle
> length, which is itself a point in favour of the decision below.

## Options considered

**A. Compute prescriptions on read.** Store the rule and cycle 1; derive cycles 2..N whenever the
UI asks. Tiny storage, no drift, one code path.
Breaks (2) entirely: there is no row to edit, so a user override has to become an exception
table — which is a materialised plan with extra steps and worse ergonomics. It also means the
displayed future silently changes as logs arrive, with no way to show *what changed and why*.

**B. Generate once, freeze.** Materialise all cycles at creation, never touch them again.
Satisfies (1) and (2), fails (3) — which is the differentiator. This is roughly what a
spreadsheet does, and the user could already use a spreadsheet.

**C. Materialise, and re-project the unstarted future.** Generate every planned set as a row up
front. After each completed session, a pure engine recomputes the cycles that have not started
yet, leaving completed, in-progress and user-locked cycles untouched.

**D. Event sourcing** — store the rule plus a log of adjustments, fold to get the current plan.
Auditable and elegant. Rejected as disproportionate: it makes the simple read ("what am I doing
Thursday?") into a fold, on a client that must do it offline, for a benefit (full history of
plan changes) nobody has asked for.

## Decision

**Option C.** Concretely:

- Every planned set is a row: `mesocycles → microcycles → planned_sessions →
  planned_exercises → planned_sets` ([03 §5](../03-database-schema.md)).
- Each microcycle carries its own `length_days` and a `status`:
  `projected | locked | in_progress | completed | skipped`.
- **The engine may only rewrite `projected` cycles** (INV-06). Everything else is the user's.
- Each planned set carries `origin` (`generated | user_edited`) and `is_pinned`. A user edit
  makes that row the new baseline; the engine projects *from* it rather than *over* it (FR-3.14).
- Projection and reconciliation are one **pure, deterministic, idempotent** function
  `project(plan, logs, now) -> plan'` (INV-10), living in `domain/` on both client and server
  ([02 §3](../02-architecture.md)).

### Why purity is a hard requirement, not a preference

Two consequences fall out of ADR-001 and they both demand it:

1. **The client must project offline.** The phone has to show the next cycle's numbers with no
   network, so the engine runs on the device.
2. **The server must project authoritatively.** So it runs there too.

If those two implementations disagree, sync thrashes: the client writes its projection, the
server rewrites it, the client pulls the change and rewrites it back. Purity plus shared
fixtures ([06 §3](../06-operations.md)) is what makes agreement checkable rather than hoped for.

Idempotence matters for the same reason — reconciliation will be triggered more than once for the
same session (a retried sync, a second device pulling the same logs), and running it twice must
change nothing.

Passing `now` as a parameter rather than calling a clock is what makes "what will cycle 9 look
like" a test, instead of a thing you can only observe by waiting nine cycles.

## Consequences

**Good**
- The whole block is visible, editable, and stable. Editing cycle 9 is an ordinary row update.
- **Variable cycle lengths cost nothing structurally.** A 9-day microcycle is just a row with
  `length_days = 9`; under option A it would have meant a date-arithmetic special case in every
  derivation.
- Reconciliation is fully testable, including adversarial cases, without a database or a clock.
- A projection bug is recoverable: fix the engine, re-run reconciliation. Only `projected` cycles
  change (INV-06), so no history is harmed ([06 §8](../06-operations.md)).
- The rule can be shown alongside the number — "62.5 kg, +2.5 kg from last cycle" — because both
  the row and the rule that produced it exist.

**Bad — accepted**
- **Row count.** A 12-cycle, 5-session, 6-exercise, 4-set programme is ~1 500 `planned_sets`. Trivial
  for Postgres, and fine for SQLite, but it does mean generation is a bulk insert and a plan edit
  can touch hundreds of rows. Batch the writes; do not loop.
- Regeneration must be careful not to clobber user edits — governed by `origin` and `is_pinned`,
  and worth aggressive property testing.
- Storage duplicates information derivable from the rule, so a rule change requires an explicit
  regeneration step rather than being instantly reflected. This is a feature: the user is told
  what will change before it changes.
- Sync must handle a plan edited on two devices. Policy: resolve at **microcycle** granularity, so
  a cycle never ends up half from one device and half from the other
  ([02 §7](../02-architecture.md)) — and, because devices run different engine versions, a
  projection from an older engine never overwrites a newer one, while a user edit always beats a
  projection (added 2026-09-10 by [ADR-004](ADR-004.md)).

## Notes on the strategies themselves

Six strategies are specified in [01 §3.2](../01-business-requirements.md); the engine dispatches
on `progression_rules.strategy` and every one of them must satisfy INV-02 (liftable loads) and
INV-05 (respect rep and RIR bounds).

**There is no product default.** The user chooses the strategy per exercise and may switch it at
any time, including mid-block (FR-3.6a) — a switch simply re-projects the remaining projected
cycles from where the user actually is. Block length (2–52 microcycles), microcycle length
(1–28 days, overridable per cycle) and deload policy (`none` / `every_n_microcycles` / `manual`)
are likewise the user's, not the app's.

This flexibility is the strongest argument for option C. Because prescriptions are rows rather
than a formula evaluated on read, **the storage model is identical for all six strategies and for
every cycle length**, and changing strategy mid-block is an ordinary re-projection rather than a
schema problem. Under option A, "which rule was in force when cycle 5 was generated" and "how long
was cycle 5" would both need modelling.

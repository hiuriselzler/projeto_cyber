# ADR-003 — GPS tracks are stored as typed streams plus a polyline, not as point rows

- **Status:** Accepted
- **Date:** 2026-09-07
- **Related:** [ADR-001](ADR-001.md), INV-13, FR-4.x, FR-5.1

## Context

A one-hour run sampled at 1 Hz is 3 600 points. Each point carries a timestamp, latitude,
longitude, altitude, accuracy, speed, and possibly heart rate and cadence. A user training six
times a week generates roughly **1.1 million points a year**, per person.

Four different consumers want that data at four different resolutions:

| Consumer | Needs |
|---|---|
| History list thumbnail | ~50 points, instantly, dozens at a time |
| Activity detail map | ~500–2 000 points, once |
| Elevation / pace / HR charts | the aligned full series |
| Recompute after a pipeline fix (INV-13) | every raw point, exactly as recorded |

And ADR-001 means all of this must also live in SQLite on the phone, and cross a possibly bad
network in between.

## Options considered

**A. One row per point.** `track_points(activity_id, seq, lat, lng, ele, t, hr, …)`.
The obvious relational answer, and queryable with SQL.
But: ~1.1 M rows/year/user in Postgres *and* in SQLite; row overhead (~40+ bytes) dwarfs the
~20 bytes of actual payload; loading one activity is a 3 600-row scan; and syncing a run is 3 600
rows through the outbox. Nobody ever asks a per-point SQL question — the access pattern is always
"give me the whole track". Paying relational costs for a non-relational access pattern.

**B. One JSON blob per activity.** `track jsonb`. Simple to write.
JSON numbers are text: a 3 600-point track is ~400 KB. Parsing it costs real time on a phone, and
there is no way to fetch a low-resolution version for a list thumbnail without parsing all of it.

**C. GPX/TCX/FIT files in object storage.** Standard, portable, exportable.
Every read is a network round trip to a second system, which breaks offline (ADR-001) outright,
and FIT parsing is a dependency. Good as an *export* format ([05 §8](../05-integrations.md)),
poor as a storage format.

**D. Typed binary streams, one row per stream kind, plus a simplified encoded polyline on the
activity row.**

## Decision

**Option D.**

```sql
cardio_activities.polyline  text  -- Google encoded polyline, Douglas–Peucker simplified
activity_streams (activity_id, kind, encoding, sample_count, data bytea)
                 -- kind: latlng | altitude | time | heartrate | cadence | velocity | moving
```

Three tiers, each matched to a consumer:

1. **Summary** — derived scalars (`distance_m`, `moving_s`, `elevation_gain_m`, …) live as plain
   columns on `cardio_activities`. The history list and all weekly totals read only these. No
   track data is touched to render a list. This is the single biggest performance win.
2. **Polyline** — a Douglas–Peucker-simplified encoded polyline on the activity row, ~2–5 KB for
   a run. Enough for the detail map and for client-rendered thumbnails ([05 §4](../05-integrations.md)).
   One column, arrives with the row, no join.
3. **Streams** — full-resolution per-sample series, one `bytea` row per kind, fetched only when
   a chart is opened. Parallel arrays sharing an index, so `time[i]`, `altitude[i]` and
   `heartrate[i]` describe the same sample. Encodings:
   - `latlng` — encoded polyline (delta + varint, ~5 bytes/point)
   - `altitude`, `velocity` — `f32_le`
   - `heartrate`, `cadence` — `i16_le`
   - `time` — delta-encoded zigzag varint (near-constant intervals compress to ~1 byte/sample)
   - `moving` — bitset, one bit per sample (INV-12's auto-pause mask)

   A 3 600-point run: ~18 KB for latlng, ~14 KB altitude, ~7 KB HR — **roughly 40 KB total
   versus ~400 KB of JSON or ~250 KB of point rows.**

**Raw points stay on the device** in a local-only `raw_gps_points` table until the activity has
synced, then are trimmed. They are never uploaded. This is what makes INV-13 honest: while the
raw data still exists, a pipeline bug found the same day is fully recoverable; after that,
recomputation is from the stored streams, which is why the streams are stored at full resolution
rather than simplified.

**Streams upload separately** from the activity row, to their own endpoint with its own 20 MB body
limit ([04 §5](../04-security-and-auth.md)). The activity appears in history as soon as its
summary syncs; charts fill in when the streams follow. On a bad connection the user gets the
important part first.

`pipeline_version` on every activity records which version of the derivation produced the stored
scalars, so the algorithm can be improved deliberately and backfilled rather than changing old
runs silently (INV-13).

## Consequences

**Good**
- History lists are a single indexed query over scalar columns. Fast at any history size.
- ~10× smaller than JSON, ~6× smaller than point rows, on both server and phone.
- Sync moves one row plus a handful of blobs per activity, not thousands of rows.
- The tiering matches the UI exactly: list → map → charts, each paying only for what it shows.
- Privacy trimming (04 §6) is straightforward — trim the arrays on-device before encoding.

**Bad — accepted**
- **The data is opaque to SQL.** No `WHERE altitude > 1000`. Accepted: no product requirement
  asks for it, and if one ever does, the answer is a derived scalar column, not a redesign.
- Encoding and decoding must be implemented twice (Python and TypeScript), like the domain layer,
  and verified with shared fixtures ([02 §3](../02-architecture.md)). Round-trip property tests
  are mandatory: encode → decode → compare within tolerance.
- Lossy by construction. `f32` altitude and the simplified polyline are not bit-exact to raw GPS.
  This is fine — GPS altitude is ±10 m anyway and the polyline is only ever drawn — but it means
  full-fidelity export must be generated from streams and will not perfectly match a
  device-recorded FIT file.
- A partial upload can leave an activity with a summary and no streams. `has_track` plus the
  presence of stream rows makes that state explicit and retryable rather than a silent hole.

## Revisit if

- Segment matching or route search is ever built — that needs PostGIS geometry and a spatial
  index, which is an additive change (a `geography(LineString)` column alongside the polyline),
  not a replacement.
- Sample rates rise sharply (e.g. 10 Hz from a watch import), at which point a time-series store
  becomes worth considering. At 1 Hz it is not.

# ADR-011 — Database roles: the API connects as a role that cannot skip row-level security

- **Status:** Accepted
- **Date:** 2026-09-11
- **Related:** INV-15, INV-16, [ADR-001](ADR-001.md), [ADR-007](ADR-007.md),
  [04 §4](../04-security-and-auth.md), [06 §1, §5](../06-operations.md),
  [task 001](../tasks/001-project-bootstrap.md), [task 002](../tasks/002-database.md),
  [task 003](../tasks/003-authentication.md), [task 015](../tasks/015-coach-tier.md)

> **Note (2026-09-14) — tables that hold nobody's data.** This ADR governs rows that belong to a user. The rate-limit
> windows of [ADR-015](ADR-015.md) belong to no one — an HMAC of an IP or an email, a window and a count — so that table
> has no owner, no policy and no function, and the app role writes it through ordinary grants. It is classified in
> [03 §11](../03-database-schema.md) like every other table. The allowlist below is unchanged.

## Context

INV-15 is enforced twice: a repository layer that cannot build an unscoped query, and Postgres
row-level security underneath it, so that a missed `WHERE user_id = …` returns nothing rather than
someone else's training history. [04 §4](../04-security-and-auth.md) calls RLS the second line of
defence, and [task 003](../tasks/003-authentication.md) carries a test proving it.

Nothing said **which database role the API connects as** — and that decides whether RLS exists at all.
Postgres does not apply row-level security to:

- **superusers** — and the `postgres:16` Docker image's default user is one;
- **roles with `BYPASSRLS`** — which a managed provider's default admin user may well have;
- **a table's owner**, unless the table has `FORCE ROW LEVEL SECURITY` — and the role that runs
  migrations owns every table it creates.

The path of least resistance — one connection string, shared by Alembic and the API, using the
credentials the database came with — hits all three. RLS would be enabled on every table, every policy
would be correct, and none of it would ever run. The failure is invisible to the test meant to catch
it, too: a test that connects the way the app connects sees nothing filtered and passes.
[Task 001](../tasks/001-project-bootstrap.md) creates the database, so this choice is made there
whether or not anyone makes it deliberately.

A second problem appears the moment RLS does work. **Some legitimate queries have no user yet.** Login
finds a user by email; refresh finds a token by its hash; password reset and email verification redeem
a token before knowing whose it is; retention jobs purge expired rows across all users
([04 §7](../04-security-and-auth.md)). Under policies that fail closed, every one of them returns
nothing — and the obvious fix, "let the API connect as a role that skips RLS", switches the defence off
for every table to make a handful of queries work.

## Options considered

**A. One role for everything.** Simplest to set up. RLS is decorative: the role owns the tables or
bypasses RLS, so it is exempt from every policy. Rejected — it keeps the documentation of a defence and
removes the defence.

**B. A non-owner application role, with the authentication tables exempt from RLS.** The API connects
as a role that cannot skip RLS, and `users`, `refresh_tokens` and the token tables simply carry no
policy, so login works. Rejected: those tables hold email addresses, password hashes and session
tokens — exactly where a missed `WHERE` does the most harm. Exempting the most sensitive tables from the
second line of defence in order to keep it on the rest is backwards.

**C. A separate authentication role and connection pool,** allowed to read the auth tables unscoped,
used only by the auth routers. Workable, and a stronger boundary on paper. Rejected for v1: two pools, a
rule for which code may use which, and a bypass covering *any* query issued on that pool — including
the ones nobody meant to route there. Its value depends on code review keeping the pools apart, which is
precisely the discipline RLS exists so that we need not depend on.

**D. A non-owner application role, fail-closed policies everywhere, and every legitimate unscoped query
as a named `SECURITY DEFINER` function.** The API can reach a row without a user scope only by calling a
function that exists for one purpose, returns the minimum columns, and is on a list CI enforces.
**Chosen.**

## Decision

**Option D.**

### Two roles

| Role | Superuser | `BYPASSRLS` | Owns tables | Used by |
|---|---|---|---|---|
| `cyberathlete_migrator` | no | **yes** | **yes** | Alembic, seeds, batched backfills ([06 §4](../06-operations.md)), the deploy's release step |
| `cyberathlete_app` | no | **no** | **no** | The running API, and every background job the API runs |

- `cyberathlete_migrator` has `BYPASSRLS` because backfills legitimately touch every user's rows. That
  is exactly why the API never uses it, and why its credentials are **absent from the running API's
  environment** outside local development.
- `cyberathlete_app` holds DML grants on application tables — through `ALTER DEFAULT PRIVILEGES`, so a
  new table cannot be forgotten — no DDL, and **no membership in any role that owns tables or bypasses
  RLS**. Membership would let it `SET ROLE` its way out.
- The Docker image's `postgres` user and a managed provider's admin user exist only to create these two
  roles. **One idempotent SQL script creates them everywhere**: the compose init step runs it locally,
  and it is run once by hand per managed environment. Neither admin credential is ever given to the API
  or to CI.

### Policies

- Every user-owned table has RLS **enabled and `FORCE`d**. With the API never owning a table, `FORCE` is
  a backstop rather than the mechanism: it keeps a mistaken `ALTER TABLE … OWNER TO` from quietly
  exempting that table.
- **Policies fail closed:**
  `USING (user_id = NULLIF(current_setting('app.user_id', true), '')::uuid)` — `id` in place of `user_id`
  on `users` itself. Unset or empty means zero rows. `WITH CHECK` carries the same expression, so a row
  cannot be written into another user's scope either (INV-16: a client may choose an ID, never an
  owner).
- The scope is set with **`SET LOCAL app.user_id`** inside each transaction, and nowhere else. A plain
  `SET` outlives the transaction on a pooled connection and hands one user's scope to the next request;
  it is banned.
- **The global exercise catalog is the one mixed table** ([04 §4](../04-security-and-auth.md)): rows with
  `owner_user_id IS NULL` are readable by every user and writable by none through the API; custom
  exercises follow the ordinary policy. Pure reference tables with no owner at all (`sport_profiles`,
  `gamification_tracks`, `muscle_groups`) carry no user policy and are granted read-only.

### Unscoped queries are named functions

Every operation that legitimately needs a row before a user is known, or across users, is a
`SECURITY DEFINER` function owned by `cyberathlete_migrator`:

| Function (indicative names) | Why it cannot be scoped | Returns |
|---|---|---|
| `auth_find_user_by_email(email)` | Login and reset requests do not yet know who is asking | id and password hash — no profile |
| `auth_find_refresh_token(token_hash)` | Refresh identifies the user *by* the token | the token row, for rotation and reuse detection |
| `auth_redeem_reset_token(token_hash)` | The token is how the user is identified | user id, expiry, used flag |
| `auth_redeem_verification_token(token_hash)` | As above | user id, email, expiry, used flag |
| `maintenance_purge_revoked_tokens(before)` | Retention runs across users ([04 §7](../04-security-and-auth.md)) | a count |
| `maintenance_accounts_due_for_deletion(now)` | The grace-period sweep has to find accounts to delete | user ids only |

Once a function has returned a user id, the flow sets `app.user_id` and continues **scoped**: the
deletion sweep deletes each account inside that account's own scope. **Registration** sets the scope to
the new account's id before inserting it, and the **RevenueCat webhook** sets it from the verified
payload's user id — neither needs a function.

Every such function:
- pins `search_path`, contains no dynamic SQL, and returns the fewest columns its flow needs;
- has `EXECUTE` revoked from `PUBLIC` and granted to `cyberathlete_app` alone;
- is called from exactly one API module, `repositories/unscoped.py`, importable only by the
  authentication and maintenance services ([responsibility-map](../responsibility-map.md));
- **appears on an allowlist checked by the task-002 schema script.** A `SECURITY DEFINER` function not on
  the list fails CI, so adding one is a visible change reviewed as a security boundary, never a quiet
  convenience.

### The API checks its own role at boot

The web process **refuses to start** if its database role:
- is a superuser, or has `BYPASSRLS`;
- owns any table in the application schema;
- is a member of any role that does either.

Outside local development it also refuses to start if the migrator's connection string is present in
its environment. A misconfigured deploy fails at startup, in the logs, instead of silently in a breach.

## Consequences

**Good**
- **RLS actually runs**, in every environment — including a developer's laptop, which is where RLS bugs
  are cheapest to find.
- The most sensitive tables — credentials, sessions, tokens — are inside the second line of defence, not
  exempted from it.
- The complete list of ways the API can read a row without a user scope is short, named, and enforced by
  CI. Reviewing cross-user access means reviewing one list.
- A remote-code-execution bug in the API reaches the data only as `cyberathlete_app`: no DDL, no bypass,
  and no migrator credentials in its environment to escalate with.
- The design extends to the Coach tier ([task 015](../tasks/015-coach-tier.md)) without changing shape:
  a coach's access becomes an additional policy clause over a consent grant — never a relaxation, never
  a bypass role.

**Bad — accepted**
- **Two connection strings, and a provisioning step per environment.** No managed provider creates these
  roles; somebody runs the script once, and the environment is not ready until they have.
- **The first lookup in login-adjacent code cannot use the ordinary repository layer**; it calls a
  function. A small, deliberate inconvenience, in a handful of places.
- **Local development is less forgiving.** A query that "works in psql" as `postgres` returns nothing to
  the API. That is the point, and it will still cost somebody an hour the first time.
- **`SECURITY DEFINER` functions are the new place to get this wrong.** A missing `search_path` pin or an
  over-wide return is a real vulnerability. The allowlist makes them visible; it does not make them
  correct, and each one needs a real review.
- **Pooling must respect transactions.** `SET LOCAL` is correct under transaction-mode pooling; any setup
  that splits one logical transaction across connections is unsupported.

## Revisit if

- **The function allowlist grows past about ten entries.** Cross-user access would have stopped being
  exceptional, and option C — a separate, audited authentication role — deserves a second look.
- **A managed provider prevents a non-owner, non-`BYPASSRLS` application role**, or grants privileges to
  the application's path that cannot be revoked. Choose a different provider before weakening this ADR.
- **The Coach tier ([task 015](../tasks/015-coach-tier.md)) is designed.** Its policies extend these, and
  its threat model reviews this ADR first.
- **Anything proposes connecting the API as the migrator**, "temporarily". The answer is a function on
  the allowlist, or no.

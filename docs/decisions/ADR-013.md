# ADR-013 — The schema enforces itself: child ownership, foreign-key actions and the INV-06 write marker

- **Status:** Accepted
- **Date:** 2026-09-12
- **Related:** INV-06, INV-11, INV-15, INV-16, INV-18, INV-21, [ADR-002](ADR-002.md), [ADR-004](ADR-004.md),
  [ADR-011](ADR-011.md), [03](../03-database-schema.md), [02 §7](../02-architecture.md),
  [task 002](../tasks/002-database.md), [task 006](../tasks/006-sync-layer.md)

## Context

Planning [task 002](../tasks/002-database.md) against [03](../03-database-schema.md) found four places where the
schema, as written, could not enforce what the invariants say the database enforces.

**1. Most user data had no owner column.** INV-15 and 03's conventions say every user-owned table carries
`user_id`, and 03 §11 wants a `user_id` index on every user-owned root. Yet thirteen child tables —
`set_logs`, `workout_exercises`, `routine_exercises`, `microcycles`, `planned_sessions`,
`planned_exercises`, `planned_sets`, `activity_segments`, `activity_streams`, `cardio_plan_microcycles`,
`cardio_plan_cycle_targets`, `planned_cardio_sessions`, `exercise_secondary_muscles` — had none. A
row-level security policy has nothing to compare against on those tables.

And there is a second hole beneath the first. **Postgres checks foreign keys without row-level security.**
A client that learns or guesses another user's UUID can insert a set pointing at that user's workout: the
foreign key is satisfied, the policy on the child only looks at the child. The same reference confirms the
UUID exists, and — because the referenced row can then not be deleted — lets one user block another
user's account deletion.

**2. `RESTRICT` breaks account deletion.** 03 §10 made every reference to `exercises` `RESTRICT`, so that
an exercise with history can never be deleted (INV-11). Account deletion is the one real delete, and it
cascades from `users` both to the user's custom exercises and to the workouts that reference them. A
`RESTRICT` check runs the moment the exercise row goes, before the cascade has necessarily reached the
referencing sets — so whether deleting an account succeeds would depend on the order Postgres happens to
fire its cascade triggers.

**3. INV-06's trigger had no way to tell who was writing.** Task 002 asks for a trigger rejecting an update
to a planned set in a cycle that is no longer `projected`, "unless the session flags itself as a user
edit" — without saying how. SQLite, which must carry the same trigger, has no session variables. And any
marker has to let **replication** through: a device applying a cycle that another device completed is
neither the engine nor the user, and a new device pulls completed cycles as ordinary inserts.

**4. A NULL defeats INV-21's key.** `xp_awards` is unique on `(user_id, source_kind, source_id, reason)`,
and `source_id` is nullable. SQL treats two NULLs as distinct, so two `manual` awards with the same reason
and no source would both be accepted — the double award the constraint exists to prevent.

## Options considered

### 1. Scoping child tables

**A. Policies that walk up to the owning root** with `EXISTS` subqueries. No new columns. Rejected:
`planned_sets` would need four nested lookups on every read, on the tables the app reads most — and the
foreign-key hole stays open, because a policy on the child still cannot see which user the parent belongs to
when the reference is checked.

**B. Copy `user_id` onto every child, and make the reference to the parent carry it.** A composite foreign
key `(parent_id, user_id) → parent (id, user_id)` can only be satisfied by a parent owned by the same user,
so a cross-user reference fails as a foreign-key violation whatever the policies say. **Chosen.**

### 2. The foreign-key action for exercises

**A. `RESTRICT`**, as documented. Rejected, for the ordering failure above.

**B. `NO ACTION`.** Rejects deleting an exercise that has history with the same `foreign_key_violation`, but
checks at the end of the statement — after an account deletion's cascade has removed the referencing rows
too. **Chosen.**

### 3. The INV-06 marker

**A. A session variable** (`SET LOCAL app.write_kind`). Rejected: SQLite has none, so the device — where an
older engine is most likely to run — would need a different mechanism, and "unset" would have to mean
"engine", making every write path responsible for declaring itself.

**B. The row carries the marker it already has.** A planned set says who shaped it (`origin`); a microcycle
says who last wrote it (`last_write_kind`). The trigger reads those, and only fires when a prescription
actually changes. **Chosen.**

### 4. The NULL in INV-21's key

**A. Make `source_id` NOT NULL.** Rejected: a manual award genuinely has no source row.

**B. Treat NULLs as equal in the key** — `UNIQUE NULLS NOT DISTINCT` in Postgres, and in SQLite, which lacks it, a
second unique index over the rows with no `source_id`. **Chosen.**

## Decision

### Ownership of child rows

- **Every child of a user-owned table carries `user_id uuid NOT NULL → users ON DELETE CASCADE`, indexed** —
  roots and dependents alike. Every parent a child references gains `UNIQUE (id, user_id)`.
- **The reference to the parent is composite**, `(parent_id, user_id) → parent (id, user_id)`. A nullable
  link — a workout's planned session, a logged set's planned set, a planned exercise's rule — uses
  `ON DELETE SET NULL (parent_id)`, so the link is cleared and the owner is not (INV-18).
- **References to `exercises` are checked by trigger instead**, because a global catalog row has no owner
  to match: the referenced exercise must be global or owned by the referencing row's user.
- **`exercise_secondary_muscles` is the one exception.** It belongs to the mixed catalog, where a global
  exercise's muscles have no owner. It carries no `user_id`; its policy reads through `exercises`, whose own
  policy then applies. It is small and rarely written.
- **Every row-level security policy compares `user_id`** (`owner_user_id` on `exercises`, `id` on `users`),
  as ADR-011 already specifies.
- **On the device** the `user_id` columns exist too — the two schemas keep the same column names, and sync
  payloads carry the owner. The composite keys and the exercise-owner trigger are server-only: a device
  holds one user's rows, and the server is where another user's rows live.

### Foreign-key actions

- References to `exercises` from history and plans are **`NO ACTION`**. The observable rule is unchanged:
  deleting an exercise that has history fails.
- `sport_profiles` stays `RESTRICT` — no cascade ever deletes it.

### The INV-06 write marker

- **Planned sets** (`planned_sets`, `planned_cardio_sessions`): an `UPDATE` that changes a prescription —
  the targets, the set's type or index, `was_clamped`, `deleted_at` — while the owning cycle is not
  `projected` is **rejected unless `NEW.origin = 'user_edited'`**. A user who edits a set in a started cycle
  marks it as theirs, which FR-3.14 already requires.
- **Microcycles** (`microcycles`, `cardio_plan_microcycles`): an `UPDATE` with
  `NEW.last_write_kind = 'engine'` is **rejected if the cycle was not `projected` and any of its own columns
  change**, or **if it would lower `engine_version`**.
- **Unchanged rewrites pass.** Sync resends whole rows; a row written back identical is not a rewrite.
- **Inserts and hard deletes are not guarded.** A new device pulls completed cycles as inserts, and plan
  rows are only ever hard-deleted by an account-deletion cascade (INV-11).
- The same triggers exist in Postgres and in SQLite, with the same conditions.

### INV-21's key

`xp_awards` is `UNIQUE NULLS NOT DISTINCT (user_id, source_kind, source_id, reason)` in Postgres, and
in SQLite unique over `(user_id, source_kind, source_id, reason)` and, partially, over
`(user_id, source_kind, reason) WHERE source_id IS NULL`.

`invariants.md` is not changed. INV-15 already says every user-owned table carries `user_id`; INV-06
already names a trigger backstop in both databases; INV-21 already names the unique key. This ADR is how
each of those sentences becomes true.

## Consequences

**Good**
- **A missed `WHERE` returns nothing on every table**, with one flat comparison per policy.
- **Another user's rows cannot be referenced**, confirmed or blocked — by construction, not by review.
- Account deletion cascades cleanly, and deleting an exercise with history still fails.
- The INV-06 backstop behaves identically on the phone and the server, and lets replication through.
- Task 006's per-row ownership check (INV-15) is a column comparison, not a walk up the tree.

**Bad — accepted**
- **A `user_id` column and an index on thirteen more tables**, and a `UNIQUE (id, user_id)` on each parent.
  A few bytes per row, and a second index on parents that already have one on `id`.
- **The marker is only as honest as the code that sets it.** A bug that stamps `user_edited` on an engine
  write passes the trigger. The backstop catches the realistic failure — the engine re-projecting a cycle it
  should have left alone — not a deliberate lie.
- **Planned sessions and planned exercises carry no marker**, so the trigger guards the prescriptions
  themselves (the sets) and the cycle row, not the session and exercise rows between them.
- **Sync must apply a resolved cycle in a way the guard allows** — its children before the cycle's new
  status, or by replacing them. Recorded in [task 006](../tasks/006-sync-layer.md).
- `ON DELETE SET NULL (column)` needs Postgres 15 or later. The project runs 16.

## Revisit if

- A second writer that is neither the engine nor the user — an import, a coach (task 015) — needs to change
  a started cycle. That is a new `origin` / `last_write_kind` value, decided here, never a trigger exemption.
- Row-level security on the child tables shows up in query plans as a real cost. Measure before touching it.

## Context

The developer knows C, C++, Rust, JavaScript and Python, and asked whether each language should be
placed where it handles the problem best.

Usually that question deserves a sceptical answer — a polyglot stack on a solo project is a tax
paid every day for elegance enjoyed occasionally. But this architecture has one specific,
already-documented wound that a second language closes exactly.

[ADR-001](ADR-001.md) puts a full database on the phone, so the client must compute
independently. [ADR-002](ADR-002.md) requires that the progression engine be pure and produce
**identical** results on client and server, or sync thrashes forever (INV-10). The current answer
in [02 §3](../02-architecture.md) is to write that logic **twice** — Python and TypeScript — and
police the two copies with shared JSON fixtures. It is described there as a deliberate cost.

The duplicated surface is not small:

| Logic | Why it must be identical |
|---|---|
| Progression engine (6 strategies, reconciliation) | Client projects offline, server re-projects; disagreement = sync thrash |
| Load rounding (INV-02) | A 0.5 kg difference makes every downstream cycle diverge |
| e1RM (INV-07) | Feeds `percent_1rm` prescriptions and PRs |
| GPS pipeline (filter, smooth, accumulate, split) | Client computes on finish, server must reproduce (INV-13) |
| Stream codecs ([ADR-003](ADR-003.md)) | Encoded on the phone, decoded on the server, and vice versa |
| HR zones, volume aggregation | Every total on every screen must match |

Fixtures catch divergence *after* it is written. They do not prevent it, and they do not cover
inputs nobody thought of. Two implementations of a rounding rule will eventually disagree on a
float boundary, and the failure mode is a training block that silently drifts.

## Options considered

**A. Status quo — Python + TypeScript, shared fixtures.** No new toolchain, full OTA updates,
straightforward debugging. Permanent duplication and a whole category of latent bugs.

**B. Rust core, compiled for both.** One crate, `core-rs`, exposed to Python via **PyO3** and to
React Native via **UniFFI** (which generates the TypeScript/Kotlin/Swift bindings and the native
module). Written once, tested once, provably identical everywhere.

**C. TypeScript core everywhere** — run the domain logic in Node on the server too. Removes the
duplication with no new language, but splits the backend across two runtimes, or forces
abandoning FastAPI, which the user chose deliberately.

**D. Server-only domain logic.** Only one implementation, but it breaks offline planning outright
([ADR-001](ADR-001.md)). Rejected.

**E. C or C++ instead of Rust.** Same single-implementation benefit. Rejected: this is code doing
float arithmetic and binary decoding across an FFI boundary, and Rust's guarantees plus `cargo`
are worth more here than any familiarity advantage.

## Proposed decision

**Option B**, scoped tightly.

```
core-rs/                    #![forbid(unsafe_code)]  — no I/O, no clock, no RNG
├── progression/     6 strategies, reconciliation, rounding (INV-02, INV-05, INV-10)
├── strength/        e1RM (INV-07), volume, PR detection, is_counted_set (INV-04)
├── gps/             filter → outlier → smooth → accumulate → splits (INV-13)
├── codec/           stream encode/decode (ADR-003)
└── zones/           HR zones (INV-14)
        │
        ├── PyO3    → app.domain, imported by FastAPI services
        └── UniFFI  → a native module, imported by src/domain in the Expo app
```

**What stays where it is:**
- **Python / FastAPI** — HTTP, ORM, migrations, auth, sync orchestration. Unchanged.
- **TypeScript / React Native** — all UI, local database, sync client, recording orchestration.
  Unchanged.
- **Rust** — only the pure functions in the table above. Nothing that touches a socket, a file,
  or a screen.

The boundary rule: **if it does I/O, it is not in Rust.** That keeps the FFI surface to plain
data in, plain data out, which is where Rust interop is pleasant rather than painful.

## Consequences

**Good**
- The duplication in [02 §3](../02-architecture.md) disappears, and with it the entire class of
  client/server divergence bugs. INV-10 becomes structurally true rather than test-enforced.
- One test suite for the hardest logic in the project, in a language with real property testing
  (`proptest`) — which is exactly what [task 005](../tasks/005-strength-progression-planner.md)
  and [task 007](../tasks/007-cardio-recording.md) call for.
- Binary codecs and GPS maths are genuinely nicer in Rust than in either alternative.
- Fast enough that generating a 24-cycle block or reprocessing an hour of GPS is imperceptible.
- The shared fixtures remain valuable — as regression tests, not as a divergence tripwire.

**Bad — and these are real**
- **No OTA updates for domain changes.** `eas update` ships JS only ([05 §9](../05-integrations.md)).
  A progression-engine bugfix becomes a store release: review latency first, and then the slower
  problem — users who do not update for weeks keep running the faulty engine. With paying users
  this is a recurring cost, not a theoretical one, and it is the strongest argument against
  option B. § Decision procedure explains why it is accepted anyway, and the conditions that make
  it acceptable.
- A third toolchain: `cargo`, cross-compilation for the Android targets now and the iOS targets
  when iOS ships ([ADR-009](ADR-009.md)), and CI build time measured in minutes rather than seconds.
- The Expo app needs a custom native module. **The cost here is already paid** — background
  location already forces a development build and rules out Expo Go
  ([05 §1](../05-integrations.md)) — but it makes Expo SDK upgrades slightly more brittle.
- Debugging across the FFI boundary is worse than debugging either side alone. Keep the boundary
  to plain data specifically so this rarely matters.
- If the developer stops enjoying Rust, a solo project has no one to hand it to — and with paying
  users that is a business-continuity risk, not a hobby problem. Keeping the core small and
  plain-data-only is the mitigation: it stays readable by someone who is not a Rust specialist.

## Decision procedure — buy the information before committing

The argument above is strong but it rests on one **unverified assumption**: that the
UniFFI + PyO3 + EAS cross-compilation chain actually works, on this project, on each platform it ships on.
If it does, option B is clearly right. If it is a swamp, option A is clearly right. Committing
either way today is guessing, and the guess is cheap to eliminate.

**So: a spike in [task 001](../tasks/001-project-bootstrap.md), then a go/no-go.**

Build `round_to_increment()` (INV-02 — a dozen lines) in `core-rs`, expose it through both
bindings, and call it successfully from FastAPI *and* from the Expo app on a **physical Android
device**. Timebox: **two days.**

> **Platform scope (2026-09-10, [ADR-009](ADR-009.md)).** The app ships on Android first, so the spike
> runs on Android only, and its outcome decides the core for Android and the server. **The iOS half is
> moved, not dropped** — it is the first gate of [task 016](../tasks/016-ios-platform.md), before any
> iOS feature work. The risk this defers is stated in ADR-009: if UniFFI's React Native bindings prove
> hostile on iOS, the iOS app would need a TypeScript mirror of the engine for that platform alone.

> **What "chain works" means (decided 2026-09-11, before the spike starts).** The chain works if
> `round_to_increment()` is called through PyO3 from FastAPI, and through UniFFI from a development build
> on a physical Android device, with the Android artefacts built by CI on Linux and by EAS. Local
> cross-compilation on the Windows development machine may run in WSL2: **a native-Windows build that
> fights back while WSL2, CI and EAS work is not a failure.** The bar is set before the clock starts so
> that it cannot move during the spike.

| Outcome | Decision |
|---|---|
| Chain works within the timebox | **Option B.** The core is adopted from [task 004](../tasks/004-exercise-catalog-and-logging.md) onward — e1RM (INV-07) and `is_counted_set()` (INV-04) are its first real residents |
| Timebox blown, or the toolchain is hostile | **Option A.** Record the failure in this ADR, write the domain twice, and lean hard on the fixtures |

**Why this is the right shape of decision, rather than a hedge:**

- The genuine unknown is *toolchain risk*, not whether one implementation beats two. One
  implementation obviously beats two; the only question is what it costs.
- Two days is a cheap price for eliminating the risk, and the spike is thrown away either way.
- Discovering a native linking problem during
  [task 005](../tasks/005-strength-progression-planner.md) — under pressure, mid-engine — would
  cost far more than two days now. The same argument is why the iOS half is the *first* gate of
  task 016 rather than something discovered mid-port.
- It does **not** incur the write-it-three-times penalty this ADR warns about. Tasks 001–003
  contain essentially no shared domain logic, so nothing is written twice while the question is
  open, and the answer arrives before task 004 needs e1RM.

### Why the OTA cost does not block acceptance — with real users

The original version of this section called the cost "close to zero" because the only user was the
developer. That premise is retired, so the argument has to stand without it. It does — for four
reasons, and only on four conditions.

**Why the cost is smaller than "same-day push versus store release" suggests**

1. **OTA reaches this product's core users last.** The app is offline-first by design
   ([ADR-001](ADR-001.md)). An `eas update` lands on the next launch *with a connection*, so the
   lifter in a basement gym and the runner in the hills are precisely the users who receive it
   latest. A same-day JS push is real for online users and much weaker for the ones this app is
   built around. Option A's fix-speed advantage is narrower than it first appears.
2. **The server runs the engine too, and the server deploys in minutes.** Reconciliation is
   authoritative on the server ([ADR-002](ADR-002.md)). Under option B the server's copy is the same
   crate through PyO3, so a projection bug is fixed server-side by an ordinary deploy, and corrected
   projected cycles reach every device on its next sync — no store release involved. Only a
   device's *offline* re-projection waits for the app update.
3. **The client calls the core through JavaScript, and JavaScript ships over the air.**
   `src/domain/` is a thin TypeScript wrapper around the native module
   ([responsibility-map](../responsibility-map.md)). An OTA update can therefore **switch off** a
   faulty strategy, or stop local re-projection entirely and defer to the server, without touching
   native code. Option B gives up the ability to *patch* the engine over the air; it keeps the
   ability to *disable* it.
4. **This is the least-changing code in the project.** Pure functions, property-tested against every
   invariant, identical on both sides. The code most likely to need an urgent fix — UI, sync client,
   recording — is JavaScript, and keeps OTA under either option.

**The conditions — required before the first user who is not the developer**

1. **A client-side kill switch** for each progression strategy and for local re-projection,
   delivered as OTA-updatable configuration. Without it, reason 3 is only a possibility.
2. **An engine version on every projection, and the skew rule below.** Without it, reason 2 produces
   exactly the sync thrash INV-10 exists to prevent.
3. **Server reconciliation treated as authoritative in the sync design**
   ([task 006](../tasks/006-sync-layer.md)), not as one more last-write-wins writer.
4. **A minimum engine version enforced for re-projection only.** A device below it stops
   re-projecting locally and shows the plan as the server last projected it. It is **never** blocked
   from logging, reading history, recording or syncing — INV-26 and NFR-1 keep those available to
   every version, however old.

**If the spike succeeds but these conditions cannot be met, option A is the right answer despite a
working toolchain.** A native engine that cannot be switched off remotely is a real liability with
paying users. The toolchain question is necessary; it is not sufficient.

**Where they are built** (2026-09-11). Conditions 1, 2 and 4 are acceptance criteria of
[task 005](../tasks/005-strength-progression-planner.md), because the kill switch and the minimum engine
version live in the `src/domain/` wrapper and its over-the-air configuration. Condition 3 belongs to
[task 006](../tasks/006-sync-layer.md), where how it combines with same-version last-write-wins is still to
be written. All four in place before the first external user is a launch blocker in
[PROJECT-STATUS](../PROJECT-STATUS.md).

### The problem both options share: engine version skew

Re-arguing the OTA cost for real users exposed something invisible while one person updated every
copy of the engine at once. **A multi-user product runs many engine versions simultaneously** — some
devices never updated, some offline for a month, the server always current.

INV-10 guarantees agreement between two runs of *the same* function. Two engine versions are two
different functions. A device on version 3 and a server on version 4 project the same plan
differently, and under last-write-wins each overwrites the other on every reconciliation trigger.
That is sync thrash, following directly from INV-10's own reasoning.

**This is not a Rust problem.** Option A has it too: a TypeScript engine updated over the air still
reaches offline devices late. It is therefore required whichever way the spike goes:

- Every projected microcycle records the **engine version** that produced it — the progression
  counterpart of `pipeline_version` for GPS (INV-13).
- **A projection from an older engine never overwrites one from a newer engine**, whatever the
  timestamps say. A device that is behind yields to the server rather than fighting it.
- User edits are unaffected: `user_edited` and `is_pinned` rows belong to the user, not the engine
  (FR-3.14), and resolve on their own terms.

**Specified 2026-09-10.** `engine_version` and `last_write_kind` on both microcycle tables
([03 §5, §7](../03-database-schema.md)); the resolution table in [02 §7](../02-architecture.md); the
rule itself in INV-06; the work in [task 005](../tasks/005-strength-progression-planner.md),
[task 006](../tasks/006-sync-layer.md) and [task 009](../tasks/009-cardio-planner.md).

**What `ENGINE_VERSION` means**, so that it is bumped for the right reason: it changes **whenever any
shared fixture's expected output changes**, and at no other time. A refactor that alters no
projection does not bump it. A change that alters a projection *without* a fixture proving it is a
missing fixture, and fails review — because an unbumped behavioural change is precisely a second
engine wearing the first one's version number.

### Revisit if

- An engine defect reaches users and the kill switch could not contain it.
- Engine fixes turn out to be frequent rather than rare — which would mean reason 4 was wrong.
- The minimum-version rule ever needs to block anything other than re-projection. That would put it
  in conflict with INV-26, and INV-26 wins.

## Explicitly not proposed

- **C or C++ anywhere.** No problem here needs them that Rust does not cover better.
- **Rust for the API.** FastAPI was chosen deliberately; Axum would be a rewrite in exchange for
  performance that an API serving batched, offline-first syncs does not need at any plausible scale
  for this product ([06 §9](../06-operations.md)).
- **Rust for the UI.** No.
